# ADR 0013: Run gitleaks and osv-scanner offline from one package

- **Status:** Accepted (maintainer approval 2026-11-16, PR #223)
- **Date:** 2026-11-16
- **Deciders:** @Ludocius
- **Changes:** the exec rule in `internal/tools/budget` (one new package, `internal/scanrun`, matched exactly, and one `syscallAllowed` file for its process group); the JSON report schema v1 (`coverage.scanners[].status` gains `evaluated` and `failed`, amended additively as ADR 0009 allows before the first release); the Markdown and SARIF scanner sections and the `creep scan` text summary; the `scanners.enabled` project-file rule
- **Qualifies:** [ADR 0010](0010-optional-scanners-detect-only.md) (Consequences)
- **Amended by:** #62 (2026-11-19), #226 (2026-11-21)

## Context

ADR 0010 made gitleaks, osv-scanner and semgrep optional and detect-only: they are looked up on `PATH` and listed as not evaluated. #221 asks to run them. That is the first product code that starts another program, so it can bypass invariant 1 (network only through the gateway) and invariant 5 (no network except model endpoints), and it can execute something the scanned repository planted (invariant 4's spirit: the host runs nothing the repository chose).

Review of PR #218 found two gaps that a runner would inherit:

- Detection compared paths as strings after `filepath.EvalSymlinks`. Since Go 1.23 that no longer follows Windows junctions (mount points), and a `\\?\` verbatim `PATH` entry does not compare as inside the repository, so both were reported `not_run` instead of `refused` (tester finding 1, Low).
- The scanned repository's `creep.yaml` could set `scanners.enabled` (finding 2, Info). Once enabling means running, that is a repository choosing which programs run on the operator's machine (#62).

What each tool needs to run without the network (from each tool's documentation):

| Tool | Offline invocation | Repository-chosen config it would read | Network if misused |
|---|---|---|---|
| gitleaks v8 | `detect --no-git --source <repo>` scans files only, no git history and no `git` binary | `<repo>/.gitleaks.toml` (replaces the rules), `<repo>/.gitleaksignore` (always loaded from the source root, whatever `--gitleaks-ignore-path` says), inline `gitleaks:allow` | none |
| osv-scanner v2 | `scan source --recursive --offline` with a local database (`OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY`, laid out as `osv-scanner/<ecosystem>/all.zip`); never `--download-offline-databases`. A missing ecosystem database is logged and matches nothing | `osv-scanner.toml` per directory (ignores advisories), `.gitignore` (skips listed files) | database download, registry resolution, deps.dev |
| semgrep | `--metrics=off --config <local rules>` | `.semgrepignore`, any `--config` the repository suggests | registry rules (`--config auto`, `p/...`), metrics, version check |

## Options

| Option | Pros | Cons |
|---|---|---|
| A. Keep detect-only (ADR 0010) | No program runs | Installed tools add no coverage |
| B. Run each tool from the package that knows it (`static`, `cli`) | No new package | `os/exec` spreads across packages that also handle repository text; the exec rule loses its single review point |
| C. One package, `internal/scanrun`, is the only product code allowed `os/exec`; fixed offline invocations; everything else stays not run | One reviewed place; fixed arguments; failures are visible | gitleaks and osv-scanner only; semgrep needs rules creep does not ship |

## Decision

Option C. What decided it: one package with fixed arguments keeps the exec path as small and reviewable as the gateway keeps the network path.

**Which binary may run.** `static.DetectScanners` keeps its first-match rule and now resolves the match to its **final path**: every symbolic link and every junction is followed component by component (`os.Lstat`, `os.Readlink`, at most 64 hops), `\\?\` and `\??\` prefixes are removed, and a volume-GUID target or any error fails closed. The final path and each directory above it are then compared with the repository and the working directory by **file identity** (`os.Stat` + `os.SameFile`), so case, 8.3 names, `subst` drives and roots reached through links all match. A match inside is `refused`. The runner executes that final path, never the name looked up again, and repeats the check right before starting it (`static.OutsideRepo`). On Windows only an `.exe` runs: `CreateProcess` would run a `.bat` or `.cmd` through `cmd.exe`. No new dependency: `GetFinalPathNameByHandle` would need `golang.org/x/sys` or `unsafe`, both barred.

**Who may enable a scanner.** Only the user file, `--config` or the org policy. The project file (the scanned repository's `creep.yaml`) cannot set `scanners.enabled` at all; doing so is a config error (exit 2) that names the project file. `creep config explain` shows which layer set the key.

*Amended by #62 (2026-11-19):* this ADR first let the project file remove scanners an earlier layer enabled. A removed scanner is `not_enabled`, which never makes a run incomplete, so a pull request could drop the class that would fail its gate (`hardcoded_secret`, `vulnerable_dependency`) and still pass. Making removal mark the run incomplete would need the scan to know which layer set the key; forbidding the key in the project file is smaller and fails closed (exit 2).

**How it runs.**

- `exec.CommandContext` with the final path and a fixed argument list per tool; the repository root is the only variable and is passed as one absolute argument. No shell.
- gitleaks: `detect --no-git --source <repo> --config <tmp>/gitleaks.toml --gitleaks-ignore-path <tmp>/ignore --report-format json --report-path <tmp>/report.json --redact --no-banner --log-level error --exit-code 0`. creep's config only extends the built-in rules (`[extend] useDefault = true`), so a repository's `.gitleaks.toml` is not read. gitleaks always loads `<repo>/.gitleaksignore`, and no flag turns that off, so when the repository root holds one (any file type) gitleaks is not started: its status is `failed` (`repo_suppression_file`) and the run is incomplete, rather than evaluated with findings the repository chose to hide. A `.gitleaksignore` in a subdirectory is not read. `--redact` keeps secrets out of the report. Inline `gitleaks:allow` comments still suppress single findings: a residual risk the report cannot see.
- osv-scanner: `scan source --recursive --no-ignore --offline --config <tmp>/osv-scanner.toml --format json --output <tmp>/report.json <repo>`, with `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY` taken from the operator's environment. `--no-ignore` scans lockfiles the repository's `.gitignore` lists. Without the variable, with a relative path, or with a directory that holds no non-empty `osv-scanner/<ecosystem>/all.zip`, osv-scanner is `not_run`: it would need the network, or would report "evaluated" with nothing to match against. A database for some ecosystems but not the repository's is a residual risk: osv-scanner logs the miss and reports no advisories for it. A database inside the repository or the working directory is `refused`. The empty `--config` replaces any `osv-scanner.toml` in the repository. Exit 1 (advisories found) is success; 128 (nothing to scan) is success with no findings.
- semgrep stays detect-only (`not_run`): creep ships no local rules, and every other rule source is the network or the repository.
- Environment: only what creep sets. `PATH` is empty (no helper programs such as `git` or `go`), `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA` and `XDG_*` point at a fresh temporary home, `TMP`/`TEMP`/`TMPDIR` at a fresh temporary directory, and every proxy variable at `http://127.0.0.1:1` with `NO_PROXY` empty, so an HTTP attempt despite the offline flag fails instead of leaving the machine. `CREEP_API_KEY`, tokens and the operator's proxies are never passed. (Windows adds `SYSTEMROOT` itself.) This narrows, but cannot prove, the absence of network access: a tool could open raw sockets. The offline flags are the primary control, the environment the backstop.
- The working directory is that temporary directory, removed afterwards.
- Limits: 10 minutes per tool, a 64 MiB report, 10 000 findings. Standard output and error go to the null device.
- On timeout the whole process tree dies on Unix: the scanner runs in its own process group (`Setpgid`), which is killed with `SIGKILL` (`internal/scanrun/proc_unix.go`, the one `syscall` file allowed there). On Windows only the scanner itself is killed: a job object needs `golang.org/x/sys` or `unsafe`, both barred. A helper it started could outlive the run there (residual risk; with an empty `PATH` a tool cannot start one by name).

**How output is read.** The report file is read up to the byte cap and decoded with `encoding/json` into closed structs that hold only the file, line and the tool's rule or advisory identifiers; matches, secrets, commits and authors are never decoded. Trailing data or a wrong shape is malformed. Each path must resolve inside the repository (`filepath.IsLocal` after `filepath.Rel`), be UTF-8 and at most 4096 bytes. Rule names and advisory IDs are hashed with the path and line into an opaque 24-digit key; the report finding is `<scanner>-<key>`, class `hardcoded_secret` or `vulnerable_dependency`, status `probable`, at the reported path and line. No tool text other than a checked path reaches the report, and the report escapes paths as it does for every repository string. Scanner findings go to the report only, never to the planner (invariant 3).

**Exit codes and completeness.** Scanner findings are findings like any other: they are rated `high` for the gate (`classSeverity`), so the default PR gate (`probable:critical`) does not trip on them. A scanner that was enabled and found but **failed** (did not start, non-success exit, timeout, report missing, malformed, over a cap, or a path outside the repository) evaluated nothing: its status is `failed`, the run is incomplete with reason `scanner_failed`, and `creep scan` exits 4 (ADR 0007, ADR 0009). `not_enabled`, `missing`, `refused` and `not_run` keep ADR 0010's meaning: listed, not evaluated, and not a gap.

**`creep doctor`.** It does not exist yet (#6). Asking a tool for its version executes it, so when #6 adds versions it must go through `scanrun` with the same rules.

## Consequences

- ADR 0010's line "the refusal rules above already decide which binary may run" is qualified: only the final-path rule here decides it.
- `internal/tools/budget` gains `execAllowedExact` with `internal/scanrun` and its reason, matched exactly (a subpackage gets no exception), and a `syscallAllowed` entry for `internal/scanrun/proc_unix.go`; any other package that imports `os/exec` still fails `make budget`.
- The report schema v1 `coverage.scanners[].status` enum gains `evaluated` and `failed`; Markdown, SARIF (a warning for `failed`) and the text summary say which classes a scanner evaluated.
- Tests: `internal/static/scanners_test.go` and `scanners_windows_test.go` (now in `internal/repofile`, #265) (final path, links, cycles, `\\?\`), `internal/scanrun/run_test.go` with the test binary re-run as a fake scanner (findings, deduplication, malformed and missing report, byte and finding caps, timeout, non-zero exit, a path outside the repository, no key, proxy or `PATH` in the child, offline flags present; nothing starts for semgrep, osv-scanner without a usable database (missing, empty, empty `all.zip`), a binary or database in the repository, or gitleaks with a root `.gitleaksignore`), `proc_unix_test.go` (a helper dies with the timed-out scanner), `run_windows_test.go` (a junction into the repository, a `.cmd`), `internal/config/scanners_test.go` (project file cannot set the key, #62), `internal/cli/scanners_run_test.go` (evaluated, failed, exit codes).
- A tool version whose flags differ (for example osv-scanner v1, which used `--experimental-offline`) exits non-zero and is reported `failed`, never run in an online mode.
- Running semgrep needs creep-shipped local rules: a new ADR.

## Amendment (#226, 2026-11-21): no repository suppression, every ecosystem, Windows tree kill

- **`.gitleaksignore`.** Failing closed on any root `.gitleaksignore` made every scan of a repository that uses gitleaks in CI incomplete. The repository is untrusted, so the file must still never hide a finding; it is now left out instead of refused. gitleaks reads `<source>/.gitleaksignore` only from the root of the source it is given, so when the repository root holds one (any type), gitleaks runs once per root entry: each regular file and directory is its own `--source`, the ignore file included (a file source loads no ignore file, so it is scanned as a single run would scan it and a secret written into it is still found); links, special files and `.git` are skipped, as a single run would skip them. The runs share one timeout, one workspace (the previous report removed before each run) and the finding cap. The result carries `SkippedRepoIgnore`, and `creep scan` says on stderr and in the text summary, Markdown and SARIF that the file was not applied (`ScannerCoverage.RepoIgnoreSkipped`, not serialized); the frozen JSON v1 schema does not change, and the status is `evaluated` because nothing was hidden. A root directory that holds its own `.gitleaksignore`, or a root with more than 256 entries, leaves no clean source: gitleaks is not started, `failed` (`repo_suppression_file`), and the run is incomplete.
- **osv-scanner ecosystems.** A database that holds one ecosystem no longer reads as evaluating all of them. Before the start, `scanrun` walks the repository (no linked directory entered, a linked lockfile name counted, `.git` skipped, the job's timeout applies) and maps each lockfile and manifest name osv-scanner reads to its ecosystem (`lockfileEcosystems`, plus `*requirements*.txt` and `*.deps.json` by shape). Every ecosystem found needs a non-empty `<db>/osv-scanner/<ecosystem>/all.zip`; otherwise osv-scanner is not started, `failed` (`missing_ecosystem_db`), and the run is incomplete. A name the map has that osv-scanner does not read asks for one database too many, the strict side; a format the map lacks is the remaining residual.
- **Windows process tree.** A job object still needs `golang.org/x/sys` or `unsafe`, and no new dependency is added (invariant 6). On timeout, `proc_windows.go` runs `%SystemRoot%\System32\taskkill.exe /T /F /PID <pid>` by absolute path, with fixed arguments, an empty environment, no shell and System32 as its working directory (the repository is not on its DLL search path), then kills the scanner itself. `os/exec` closes its process handle as soon as the scanner exits, which can be before `cmd.Cancel` runs, so `runTree` opens a second handle right after the start, while the ID is still the scanner's, and holds it until `Wait` returns; taskkill runs only while that pin is held, so a reused ID never sends it to an unrelated process. A `SystemRoot` that is empty, relative, UNC or `\\?\` runs nothing and falls back to killing the scanner only. Residual: a helper whose parent already exited is no longer in the tree, and taskkill matches children by parent ID, so a process whose long-gone parent once had the same ID is in it. `internal/scanrun` stays in `execAllowedExact`; no `syscall` file is added.
- Tests: `internal/scanrun/gitleaksignore_test.go`, `osvdb_test.go`, `proc_test.go` (now on Unix and Windows; the helper beats until killed, so the check needs no fixed delay), `proc_windows_test.go` (`SystemRoot` shapes), `internal/cli/scanners_run_test.go`, `internal/report` golden files (the note in Markdown and SARIF, none in JSON).
