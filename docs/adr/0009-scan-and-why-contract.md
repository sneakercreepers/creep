# ADR 0009: `creep scan` and `creep why` contract, report v1 additions

- **Status:** Accepted (maintainer approval on #205)
- **Date:** 2026-11-16
- **Deciders:** @Ludocius
- **Changes:** the CLI contract (`scan`, `why`), the JSON report schema v1 (architecture §4), report file locations

## Context

#175 wires the pipeline (calibrate → static → planner → reader → report) into `creep scan` and builds `creep why <id>`. Both were stubs that exited 2. Wiring them fixes public behavior that nothing has decided yet:

- Where `scan` reads the repository from and where it writes reports, so `why` can find them.
- What `why` prints. The JSON report v1 has no evidence, no reason for a not-evaluated finding and no flag for a verdict from a cut slice (the #200 audit: a `not_vulnerable` from a partial slice must never read as clean).
- Which files and sinks make a run incomplete (exit 4, ADR 0007). Static analysis, the planner and the reader each leave things out, some by design (vendor code, tier S's low-risk skip) and some because they could not do better (syntax errors, caps, step and token bounds, model failures).
- How the gate (`gates.pr`, `<status>:<severity>`) is evaluated when findings carry a class but no severity.

No version has been released, so no consumer depends on report v1 yet.

## Options

| Option | Pros | Cons |
|---|---|---|
| A. Bump the report to v2 for the new fields | Follows the schema rule literally | A second schema and fixture before any release; v1 would never ship |
| B. Amend v1 additively before the first release, keep the rule from the first release on | One schema at v0.1; every new field is optional, so the committed v1 fixture still validates | v1 changes once more after #166 |
| C. Keep the report as it is and give `why` its own evidence file | No schema change | A second file format to keep in step; `why` and the report could disagree |

## Decision

Option B, and the CLI contract below. What decided it: nothing has been released, and one file (the JSON report) staying the single source for `why` is simpler than two formats.

**`creep scan [.]`** scans the current directory (the project config `creep.yaml` and `.creep/` are read from it, as `resume` does). Any other path argument exits 2. It needs `model.contract` (`openai` or `anthropic`; the command contract is #6), `model.endpoint` and `model.name`, or it exits 2 before touching the disk. The tier comes from calibration (`calibrate.RunCached`, fixed seed 1, cached in the user cache directory for `calibration.cache_days`). Reports go to `.creep/report.json`, `.creep/report.md` and `.creep/report.sarif`, per `report.formats`; each is removed and created anew inside `.creep`, never written through a planted link. Every `.creep/report.*` left from an earlier run, or planted in the repository, is removed when the run opens its state and before any model call, so a stopped run never leaves a report that reads as this run's; a name that cannot be removed exits 2. `.creep` gets a `.gitignore` of `*` on first use. `--format text` prints a summary; `json`, `sarif` and `markdown` print that report to stdout, and the incomplete mark also goes to stderr. `--record` and `--replay` use the run-state cache (#8) in `.creep/cache`.

**Exit codes** follow ADR 0007. Before a report exists: 2 for usage, configuration, consent and local errors; 3 for a failed calibration call. After it: `exitcode.ForReport`. The run is **incomplete** (exit 4) when anything that could hold a finding was not evaluated in full:

- an early stop: `run_full`, `budget`, `send_failed`, or `planner_rejected` (`planner.ErrInput`; then every class is not evaluated);
- a sink the planner skipped for `step_cap` or `budget` (the decoy-flooding mitigation from the #199 audit), a sink of a kind the planner cannot take yet (`unmapped_kind`; Express's `nosql` sinks were one until #212 mapped them), or a hypothesis the reader could not answer (`file_not_scanned`, `line_out_of_range`, `lines_shifted`, `run_full`, `invalid_output`, `inconclusive`, an unmapped kind or class);
- a verdict from a partial slice (`partial_slice`);
- a file not evaluated in full: `read_failed`, `too_large`, `not_regular`, `invalid_path` (a name static refuses, such as `a:b.py`), `parse_failed`, `syntax_error`, `truncated`, `unsupported_language` (every file whose extension is in the closed list of source languages with no grammar in `internal/cli/sourceext.go`: Go, PHP, Java, Kotlin, Scala, Ruby, C#, Rust, Elixir, C/C++ and others), and the gateway and reader reasons. Files with any other extension (markup, config, data, shell) are not source and are not listed.

Vendor, generated and minified files (a source file of any listed language under a vendor directory is `vendor`) and tier S's `low_risk` skips are left out by design: they are listed, but do not make the run incomplete. The run's reason is the first of these in that order.

**Report v1 additions** (all optional): a finding's `reason` (an ID), `partial`, `confidence` (0-100) and `evidence` (`{start, end}` line ranges); the not-evaluated file reasons `lines_shifted`, `vendor`, `generated`, `minified`, `not_regular`, `invalid_path`, `parse_failed`, `syntax_error`, `truncated` and `unsupported_language`. Finding IDs are `sink-<n>`, the static sink ID. Report classes use the calibration names (`sqli`, not the reader's `sql_injection`), plus `template_injection`; `nosql_injection` is evaluated since #212; classes the pipeline cannot evaluate yet (`idor`, `missing_auth`, `prototype_pollution`) are listed as not evaluated.

**Gate**: a probable or verified finding trips `gates.pr` by its class's severity: `sqli`, `nosql_injection` and `command_injection` critical; `path_traversal`, `ssrf` and `template_injection` high; any other class critical.

**`creep why <id>`** checks the ID against the report's ID pattern, reads `.creep/report.json` (without creating `.creep`, without blocking on a FIFO, at most 64 MiB) through `report.ReadJSON`, which refuses unknown fields and invalid findings, and prints status, class, escaped location, reason, confidence, evidence lines and the partial flag. A missing report, malformed or unknown ID exits 2.

## Consequences

- `internal/cli` holds the static→planner and planner→reader mappings as explicit switches; `plannermap_test.go` fails when either side gains a value. A static kind with no planner support yet is named in `pendingKinds` with its issue (empty since #212 mapped `static.SinkNoSQL` to `planner.SinkNoSQL` and `nosql_injection`); its sinks are listed as not evaluated (`unmapped_kind`) and never planned. The scan extracts Python with Flask and FastAPI and JavaScript, TypeScript and TSX with Express (#87).
- `reader.Signal` gains `Partial`; `reader.CallTokens` gives the planner its per-step cost.
- From the first release on, report fields change only with a `schema_version` bump, as the schema says.
- `resume` still fails closed; continuing a run needs per-step resume, a follow-up.
- `--diff`, a `--gate` choice (`gates.nightly`) and a severity per finding are not decided here.

## Follow-up: what counts as left out by design (v0.1 release pentest P4, #213)

The repository's author decides where files sit, what their first comment says and what they are named, so "by design" above let first-party code be skipped while the run read complete. Since the v0.1 release pentest, a skip needs evidence, and anything without it is read like first-party code:

- A file under a vendor-named directory is listed as `vendor` without being read only when its package manager's mark is a regular file in the repository, for that mark's language, with exact case (`static.VendorEvidence`): `node_modules/<pkg>/package.json` (or `@scope/<pkg>`) for JavaScript and TypeScript, `venv/pyvenv.cfg` or `.venv/pyvenv.cfg` for Python, `vendor/modules.txt` for Go, `composer.json` next to `vendor/` for PHP. Other names (`third_party/`, `site-packages/`, `VENDOR/`, a Python file under `node_modules/`) have no evidence.
- Every other file is read and parsed. A vendor path, a generator header or the minified shape (now nine tenths of the file's bytes on lines over 500 bytes, so one padding line is not enough; a `.min.js` name never counts) is believed only for a file that parsed without errors and holds no route. Such a file is listed with its reason and stays by design; a file with a route is extracted and evaluated like any other.
- A Go, PHP or other ungrammared file under `vendor/` without the mark is listed as `unsupported_language` and makes the run incomplete.

The report reasons and schema do not change, and every left-out file is still listed (#88). Residual: the evidence files are themselves in the repository, so an author can plant a `pyvenv.cfg` or `package.json` next to code that its language never imports from there; the file is still listed, and the planted marker shows in the pull request diff. Both residuals are closed by the last amendment below: a mark now only spares parsing a file that cannot hold a route, Go and PHP marks vouch for nothing, and the summaries count what was left out by design.

## Amendment: a run with no route is incomplete (#207)

Before #207, a repository where static extracted no route (and so no sink, since every sink belongs to a route) read as complete with every readable class `covered` and exited 0: a Django-only `views.py` with string-built SQL, Python or JavaScript without Flask, FastAPI or Express routes, or an empty repository. Every file was parsed, so nothing was listed, yet nothing was evaluated for any class.

| Option | Pros | Cons |
|---|---|---|
| A. Each class `not_evaluated`, run incomplete with reason `no_routes` (exit 4) | Reuses the incompleteness rules and exit code 4 (ADR 0007); the class status says exactly what happened; no schema or exit-code change | A repository with no web code at all (a library, a CLI tool) never exits 0 |
| B. Each readable class `partial` with a closed reason | Keeps `not_evaluated` for classes the pipeline cannot read | `partial` claims some evaluation took place; a class row has no reason field, so it needs a schema change |
| C. A new exit code | Separates "nothing to scan" from "scan cut short" | Changes the exit-code meaning (a new ADR); CI gates already treat 4 as not clean |

**Decision:** option A. When static extracts no route from the analysed files (or there is no analysable file), the scan neither plans nor calls the reader; every class is `not_evaluated`, and the run is incomplete with reason `no_routes`. The reason comes after the early stops, finding gaps and file gaps above (a Go-only repository still reads `unsupported_language`, with every class not evaluated), and before a failed scanner. The text summary prints `routes: no Flask/FastAPI/Express routes found; no class was evaluated` and the Markdown report a bold line with the same names, both from `static.FrameworkNames`, so a framework added to static is named without touching the CLI or the report. The JSON report states it through `run.reason`; the framework names are not a report field (`Report.NoRoutesIn` is `json:"-"`), so report v1 does not change. No line counts what such a run left out, since it evaluated nothing (#248): the incomplete mark reads `static found no route, so no class was evaluated` in place of a file count, the findings line says `no sink to evaluate` in place of `0 not evaluated`, and the Markdown Not evaluated section says static analysis found no route in place of `Every file was evaluated`, still listing any file left out. The scan makes no planner or reader call, but the tool canary and, on a cold cache, calibration still reach the model before static runs. A repository with at least one route is unchanged: a Flask route without sinks, or a Flask app whose sinks are all discarded, exits 0 with its classes covered.

Residual: routes of a framework static does not recognise next to one it does (Django views beside one Flask route) are still not flagged; new frameworks land with the language kits (ADR 0012, #217).

## Amendment: a mark never hides a route, and a clean run names what it left out (#213)

The follow-up above already meets most of #213. A vendor name without its mark, or with it in the wrong case (`VENDOR/`, `Node_Modules/`, `app/vendor/`, `third_party/`, `site-packages/`), is read like first-party code. A generator header or the minified shape is believed only for a file that parsed cleanly and holds no route. Two holes were left. First, a mark is itself a repository file: an author who plants one `package.json`, `pyvenv.cfg`, `modules.txt` or `composer.json` got a whole directory listed unread, so a first-party route there gave exit 0 with every class covered (the #255 tester, M1). Second, a run with by-design files read `covered` with nothing beside it.

| Option | Pros | Cons |
|---|---|---|
| A. A mark only spares parsing a file that cannot hold a route; a by-design count beside the coverage in text, Markdown and SARIF | Fail-closed: a route is evaluated wherever it sits; a real tree stays exit 0; no schema or exit-code change | Every file of a proven tree is read, and the route test must stay sound as the extractors grow |
| B. Parse every vendor file, marked or not | Simplest rule | A real tree almost always has files over the parser's 1 MiB cap or that the grammar cannot parse, so nearly every project with installed dependencies would exit 4 |
| C. Each readable class `partial` when any by-design file exists, or by-design files make the run incomplete | Strictest | A class row has no reason field (schema change), and no JavaScript or Python project with installed dependencies could pass a gate |
| D. A maintainer accepts forged marks as a residual | No code | Keeps a one-file bypass of `gates.pr` |

**Decision:** option A.

- **A mark never hides a route.** A file under a proven tree is read (up to 32 MiB) and checked with `static.MayHoldRoute`, a byte test that errs only toward true. When it is false, the file is listed as `vendor` without parsing. When it is true, the file goes through the first-party path: a route is extracted and evaluated, a route-free file that parses cleanly is `vendor`, and anything else is a gap (`too_large`, `syntax_error`, `truncated`; exit 4). The test is sound by construction, not by sampling: a Python route needs the word `route` (route or api_route decorators) or an import of `flask` or `fastapi`; an Express route needs a receiver built by `express` or a file that imports the module `express`, whose name is a literal or a `+` chain of literals. The extractor reads names as the runtime does (see the #259 bullet), and the test first folds or decodes the whole file the same way. So the bytes hold the word `express` (not `expression`), or a string literal whose whole text is a first piece of `express` or `node:express` (`"ex"`, `'node:'`), ended by its quote, a line break or the end of the file. The test reads no syntax at all: comments, strings and code count alike. A first version skipped comments to look for the `+` after a piece; a `//` comment ended by a lone CR, U+2028 or U+2029 got past it (the #255 tester's M2, cycle 2), so any lexing, which error recovery can also defeat, is out. `TestMayHoldRouteNeverMissesARoute` runs every fixture app and each hidden `require` form (every line terminator included) through the extractor and the test, as `.js` and as `.d.ts`, and a change to either that breaks the rule fails it.
- **A broken proven declaration file is `vendor` only when its code cannot hold a route (#262).** The pinned TypeScript grammar does not parse some real declaration files: router 2.x's `lib/route.d.ts`, shipped by every Express 5 install, has call signatures with generic defaults on separate lines, and `express` in a comment (the #255 tester's M3, cycle 2). A `.d.ts`, `.d.mts` or `.d.cts` file of a proven tree is still parsed and extracted (`static.Extractor.AddDeclaration`), and a route found is evaluated. When the parse has errors, the file is `vendor` only when `MayHoldRoute` is false for its bytes with the parser's comments masked. Otherwise it is `syntax_error` (exit 4), so a route in a region the grammar could not read never hides behind a mark. Only comments outside error regions are masked, and only when their own bytes prove them whole (`//` with no CR, LF, U+2028 or U+2029 inside; `/*` closed by its first `*/`). So a grammar that ends a comment later than JavaScript masks nothing it should not. Options weighed: masking only ERROR and MISSING spans (unsound, since a route call can sit in an error span while the `express` binding parses cleanly elsewhere), or failing closed on every broken declaration that holds `express` anywhere (router's comment would make every Express 5 install exit 4). The same file outside a proven tree stays `syntax_error`.
- **Go and PHP marks vouch for nothing.** Static cannot check those languages for routes, so `vendor/modules.txt` and `composer.json` no longer make a file `vendor`. Such files are `unsupported_language` (exit 4) like first-party Go or PHP. A repository with first-party Go or PHP already exits 4, so this only matters for a Python or JavaScript repository that commits a Go or PHP vendor tree.
- **A mark vouches for the native and component sources its packages ship (#261), and nothing else.** A real venv with `flask` has `markupsafe/_speedups.c`, numpy ships hundreds of headers, and native addons (`bcrypt`, `sqlite3`) ship C and C++ under `node_modules`. Inside a proven tree, `pyvenv.cfg` vouches for `.c`, `.h`, `.cc`, `.cpp`, `.cxx` and `.hpp`, and `package.json` for those and for `.vue` and `.svelte` (`static.VendorEvidence`). Such a file is `vendor` only when `static.MayHoldAnyRoute` (the Python and the JavaScript test) is false for its bytes, so a planted mark cannot hide embedded Python or JavaScript route code. A file it holds a route word in, a file too large to read, a linked file, or any other server-side language (Go, PHP, Ruby, Java, C# and the rest) stays `unsupported_language` (exit 4). Options weighed: a new by-design reason such as `vendor_native` (a report schema decision for little gain, since static cannot read these files anywhere), or keeping exit 4 with a hint (a common Flask setup could never pass). Residual: a planted mark lists a first-party C or Vue file that holds no route word as `vendor`, where it was `unsupported_language`. Static cannot read either, and none can serve a Flask, FastAPI or Express route by itself.
- **Names are read the way the runtime reads them (#259).** Python normalizes identifiers with NFKC (PEP 3131), so `@app.ｒｏｕｔｅ` registers a route. JavaScript decodes escapes in identifiers (`app.g\u0065t`) and in string literals (`"\x65xpress"`, `"\145xpress"`, `"ex\` plus a line break plus `press"`). The Python extractor folds identifier text with `nfkcASCII`, the closed table of every code point Python accepts in an identifier whose NFKC form is ASCII. It is made from the Unicode 16 data with Python's `unicodedata`: fullwidth forms, mathematical alphanumerics, letterlike symbols, ligatures, Roman numerals and modifier letters. Other code points stay as written, since their NFKC form is not ASCII and so matches no route, sink or auth name. The JavaScript extractor decodes every escape in identifiers and literals (`static.cookJS`). `MayHoldRoute` folds or decodes the whole file the same way before its search, so a planted mark cannot hide a respelled route. No dependency is added: `golang.org/x/text` would need an ADR for one table. A verb reached through a computed member (`app["get"]`, with any escape or `+` chain in the literal) or through `getattr(app, "route")` (its string unescaped, not folded, as Python reads it) is the dot form (#255 tester M4). A computed name that is not a literal on a known app or router matches every method and makes the route partial (exit 4), and the same name on an unknown receiver is no route, like any unknown attribute. A sink module reached through `__import__` or `importlib.import_module` of a literal, inline or as a module-level alias, is the imported module; a call through one whose name is not a literal makes the route partial (#255 tester I3). Cython (`.pyx`) files are `unsupported_language`, and `vendor` inside a proven venv on the same terms as C.
- **Exact case on every file system.** A mark counts only when its directory lists an entry with exactly that name as a regular file. A stat would match `PACKAGE.JSON` on Windows and macOS (the tester's L1). A linked mark proves nothing.
- **Why this is safe for real trees.** Real packages almost never hold an Express or Flask route. Library code names neither the `express` module nor a route decorator, so most files are never parsed, and a large bundle or a file the grammar cannot parse stays `vendor` when it cannot hold a route. Measured on Windows through `creep scan` with one first-party Flask route and the in-process fake model: `express` 5.3 (router 2.3), `typescript` and `mongoose` (1,269 files) exit 0 with every file `vendor`, and so does `express@4` with the same two (1,267 files). A venv with `flask`, `fastapi`, `requests` and `sqlalchemy` (1,170 Python files and `markupsafe/_speedups.c`) exits 0 with all 1,171 files `vendor` (#261), and so does `bcrypt` 5 with its C++ addon sources (271 files). `sqlite3` 5 pulls in `node-gyp`, whose `lib/Find-VisualStudio.cs` is C# and stays `unsupported_language`: that tree exits 4, by the rule that no mark vouches for another server-side language. These checks were re-run after the #259, #261 and #262 changes. A package that does ship an example or test app with a route has it evaluated like first-party code: its findings are reported, or the run is incomplete. That is the fail-closed side, and it shows in the report.
- **A clean run names what it left out.** `report.ByDesignSummary` counts the listed files whose reason is by design (`report.SkipReason.ByDesign`: `vendor`, `generated`, `minified`), in that fixed order. It holds only counts and reason IDs, never a path. The text summary prints `coverage excludes N files left out by design (vendor a, generated b, minified c), listed above` under the coverage line. Markdown prints a bold `No class covers the N files left out by design (…)` under the class table, and SARIF adds a `creep/by-design` note to the invocation's notifications. Nothing is printed when no file was left out by design. The CLI decides incompleteness with the same `ByDesign` method, so the count and the rule cannot drift. The JSON report and its schema do not change.

Residual: the route test follows the extractors. A framework or route form added to static must extend `MayHoldRoute` in the same change, and the soundness test fails until it does. The same holds for a new spelling the extractors learn to read: `TestRespelledFixturesExtractTheSame` runs each respelled fixture through both. A sink outside any route is not a static sink in any file. So a route-free vendor or generated helper called from a first-party route is no weaker than a first-party helper in another file: static does not follow calls across files for any file (`internal/static/doc.go`).
