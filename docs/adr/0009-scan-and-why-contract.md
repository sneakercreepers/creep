# ADR 0009: `creep scan` and `creep why` contract, report v1 additions

- **Status:** Accepted (maintainer approval on #205)
- **Date:** 2026-11-16
- **Deciders:** @Ludocius
- **Changes:** the CLI contract (`scan`, `why`), the JSON report schema v1 (architecture §4), report file locations
- **Amended by:** [ADR 0032](0032-resume.md) (`creep resume` continues an interrupted scan), [ADR 0020](0020-poc-repetitions-and-bundle.md) (a PoC's rate in text, Markdown and SARIF; `creep reproduce`), [ADR 0022](0022-baseline-and-accepted-risks.md) (the gate skips suppressed findings; report v1 gains `fingerprint` and `suppression`; `creep accept`), [ADR 0021](0021-gate-per-mode.md) (a gate per scan mode; the sandbox runs only in a nightly scan), [ADR 0024](0024-discovery-stability.md) (`--stability N`; report v1 gains `stability` on a finding)

## Context

#175 wires the pipeline (calibrate → static → planner → reader → report) into `creep scan` and builds `creep why <id>`. Both were stubs that exited 2. Wiring them fixes public behavior that nothing has decided yet:

- Where `scan` reads the repository from and where it writes reports, so `why` can find them.
- What `why` prints. The JSON report v1 has no evidence, no reason for a not-evaluated finding and no flag for a verdict from a cut slice (the #200 audit: a `not_vulnerable` from a partial slice must never read as clean).
- Which files and sinks make a run incomplete (exit 4, ADR 0007). Static analysis, the planner and the reader each leave things out, some by design (vendor code, tier S's low-risk skip) and some because they could not do better (syntax errors, caps, step and token bounds, model failures).
- How the gate (`gates.pr`, `<status>:<severity>`) is evaluated when findings carry a class but no severity.

No version has been released, so no consumer depends on report v1 yet.

## Options

| Option | Pros | Cons |
|---|---|---|
| A. Bump the report to v2 for the new fields | Follows the schema rule literally | A second schema and fixture before any release; v1 would never ship |
| B. Amend v1 additively before the first release, keep the rule from the first release on | One schema at v0.1; every new field is optional, so the committed v1 fixture still validates | v1 changes once more after #166 |
| C. Keep the report as it is and give `why` its own evidence file | No schema change | A second file format to keep in step; `why` and the report could disagree |

## Decision

Option B, and the CLI contract below. What decided it: nothing has been released, and one file (the JSON report) staying the single source for `why` is simpler than two formats.

**`creep scan [.]`** scans the current directory (the project config `creep.yaml` and `.creep/` are read from it, as `resume` does). Any other path argument exits 2. It needs `model.contract` (`openai` or `anthropic`; the command contract is #6), `model.endpoint` and `model.name`, or it exits 2 before touching the disk. The tier comes from calibration (`calibrate.RunCached`, fixed seed 1, cached in the user cache directory for `calibration.cache_days`). Reports go to `.creep/report.json`, `.creep/report.md` and `.creep/report.sarif`, per `report.formats`; each is removed and created anew inside `.creep`, never written through a planted link. Every `.creep/report.*` left from an earlier run, or planted in the repository, is removed when the run opens its state and before any model call, so a stopped run never leaves a report that reads as this run's; a name that cannot be removed exits 2. `.creep` gets a `.gitignore` of `*` on first use. `--format text` prints a summary; `json`, `sarif` and `markdown` print that report to stdout, and the incomplete mark also goes to stderr. `--record` and `--replay` use the run-state cache (#8) in `.creep/cache`.

**Exit codes** follow ADR 0007. Before a report exists: 2 for usage, configuration, consent and local errors; 3 for a failed calibration call. After it: `exitcode.ForReport`. The run is **incomplete** (exit 4) when anything that could hold a finding was not evaluated in full:

- an early stop: `run_full`, `budget`, `send_failed`, or `planner_rejected` (`planner.ErrInput`; then every class is not evaluated);
- a sink the planner skipped for `step_cap` or `budget` (the decoy-flooding mitigation from the #199 audit), a sink of a kind the planner cannot take yet (`unmapped_kind`; Express's `nosql` sinks were one until #212 mapped them), or a hypothesis the reader could not answer (`file_not_scanned`, `line_out_of_range`, `lines_shifted`, `run_full`, `invalid_output`, `inconclusive`, an unmapped kind or class);
- a verdict from a partial slice (`partial_slice`);
- a file not evaluated in full: `read_failed`, `too_large`, `not_regular`, `invalid_path` (a name static refuses, such as `a:b.py`), `parse_failed`, `syntax_error`, `truncated`, `unsupported_language` (every file whose extension is in the closed list of source languages with no grammar in `internal/cli/sourceext.go`: Go, PHP, Java, Kotlin, Scala, Ruby, C#, Rust, Elixir, C/C++ and others), and the gateway and reader reasons. Files with any other extension (markup, config, data, shell) are not source and are not listed.

Vendor, generated and minified files (a source file of any listed language under a vendor directory is `vendor`) and tier S's `low_risk` skips are left out by design: they are listed, but do not make the run incomplete. The run's reason is the first of these in that order.

**Report v1 additions** (all optional): a finding's `reason` (an ID), `partial`, `confidence` (0-100) and `evidence` (`{start, end}` line ranges); the not-evaluated file reasons `lines_shifted`, `vendor`, `generated`, `minified`, `not_regular`, `invalid_path`, `parse_failed`, `syntax_error`, `truncated` and `unsupported_language`. Finding IDs are `sink-<n>`, the static sink ID. Report classes use the calibration names (`sqli`, not the reader's `sql_injection`), plus `template_injection`; `nosql_injection` is evaluated since #212; classes the pipeline cannot evaluate yet (`idor`, `missing_auth`, `prototype_pollution`) are listed as not evaluated.

**Gate**: a probable or verified finding trips `gates.pr` by its class's severity: `sqli`, `nosql_injection` and `command_injection` critical; `path_traversal`, `ssrf` and `template_injection` high; any other class critical.

**`creep why <id>`** checks the ID against the report's ID pattern, reads `.creep/report.json` (without creating `.creep`, without blocking on a FIFO, at most 64 MiB) through `report.ReadJSON`, which refuses unknown fields and invalid findings, and prints status, class, escaped location, reason, confidence, evidence lines and the partial flag. A missing report, malformed or unknown ID exits 2.

## Consequences

- `internal/cli` holds the static→planner and planner→reader mappings as explicit switches; `plannermap_test.go` fails when either side gains a value. A static kind with no planner support yet is named in `pendingKinds` with its issue (empty since #212 mapped `static.SinkNoSQL` to `planner.SinkNoSQL` and `nosql_injection`); its sinks are listed as not evaluated (`unmapped_kind`) and never planned. The scan extracts Python with Flask and FastAPI and JavaScript, TypeScript and TSX with Express (#87).
- `reader.Signal` gains `Partial`; `reader.CallTokens` gives the planner its per-step cost.
- From the first release on, report fields change only with a `schema_version` bump. Amended by the #26 amendment below: there is no report v2, and v1 changes additively only, as the schema now says.
- `resume` still fails closed; continuing a run needs per-step resume, a follow-up. Superseded by [ADR 0032](0032-resume.md): `creep resume` continues the run.
- `--diff`, a `--gate` choice (`gates.nightly`) and a severity per finding are not decided here. Incremental scans are decided in the #26 amendment below (`--changed`).

## Follow-up: what counts as left out by design (v0.1 release pentest P4, #213)

The repository's author decides where files sit, what their first comment says and what they are named, so "by design" above let first-party code be skipped while the run read complete. Since the v0.1 release pentest, a skip needs evidence, and anything without it is read like first-party code:

- A file under a vendor-named directory is listed as `vendor` without being read only when its package manager's mark is a regular file in the repository, for that mark's language, with exact case (`static.VendorEvidence`): `node_modules/<pkg>/package.json` (or `@scope/<pkg>`) for JavaScript and TypeScript, `venv/pyvenv.cfg` or `.venv/pyvenv.cfg` for Python, `vendor/modules.txt` for Go, `composer.json` next to `vendor/` for PHP. Other names (`third_party/`, `site-packages/`, `VENDOR/`, a Python file under `node_modules/`) have no evidence.
- Every other file is read and parsed. A vendor path, a generator header or the minified shape (now nine tenths of the file's bytes on lines over 500 bytes, so one padding line is not enough; a `.min.js` name never counts) is believed only for a file that parsed without errors and holds no route. Such a file is listed with its reason and stays by design; a file with a route is extracted and evaluated like any other.
- A Go, PHP or other ungrammared file under `vendor/` without the mark is listed as `unsupported_language` and makes the run incomplete.

The report reasons and schema do not change, and every left-out file is still listed (#88). Residual: the evidence files are themselves in the repository, so an author can plant a `pyvenv.cfg` or `package.json` next to code that its language never imports from there; the file is still listed, and the planted marker shows in the pull request diff. Both residuals are closed by the last amendment below: a mark vouches only for a tree git does not track, Go and PHP marks vouch for nothing, and the summaries count what was left out by design.

## Amendment: a run with no route is incomplete (#207)

Before #207, a repository where static extracted no route (and so no sink, since every sink belongs to a route) read as complete with every readable class `covered` and exited 0: a Django-only `views.py` with string-built SQL, Python or JavaScript without Flask, FastAPI or Express routes, or an empty repository. Every file was parsed, so nothing was listed, yet nothing was evaluated for any class.

| Option | Pros | Cons |
|---|---|---|
| A. Each class `not_evaluated`, run incomplete with reason `no_routes` (exit 4) | Reuses the incompleteness rules and exit code 4 (ADR 0007); the class status says exactly what happened; no schema or exit-code change | A repository with no web code at all (a library, a CLI tool) never exits 0 |
| B. Each readable class `partial` with a closed reason | Keeps `not_evaluated` for classes the pipeline cannot read | `partial` claims some evaluation took place; a class row has no reason field, so it needs a schema change |
| C. A new exit code | Separates "nothing to scan" from "scan cut short" | Changes the exit-code meaning (a new ADR); CI gates already treat 4 as not clean |

**Decision:** option A. When static extracts no route from the analysed files (or there is no analysable file), the scan neither plans nor calls the reader; every class is `not_evaluated`, and the run is incomplete with reason `no_routes`. The reason comes after the early stops, finding gaps and file gaps above (a Go-only repository still reads `unsupported_language`, with every class not evaluated), and before a failed scanner. The text summary prints `routes: no Flask/FastAPI/Express routes found; no class was evaluated` and the Markdown report a bold line with the same names, both from `static.FrameworkNames`, so a framework added to static is named without touching the CLI or the report. The JSON report states it through `run.reason`; the framework names are not a report field (`Report.NoRoutesIn` is `json:"-"`), so report v1 does not change. No line counts what such a run left out, since it evaluated nothing (#248): the incomplete mark reads `static found no route, so no class was evaluated` in place of a file count, the findings line says `no sink to evaluate` in place of `0 not evaluated`, and the Markdown Not evaluated section says static analysis found no route in place of `Every file was evaluated`, still listing any file left out. The scan makes no planner or reader call, but the tool canary and, on a cold cache, calibration still reach the model before static runs. A repository with at least one route is unchanged: a Flask route without sinks, or a Flask app whose sinks are all discarded, exits 0 with its classes covered.

Residual: routes of a framework static does not recognise next to one it does (Django views beside one Flask route) are still not flagged; new frameworks land with the language kits (ADR 0012, #217).

## Amendment: only an installed tree is vendor, and a clean run names what it left out (#213)

The follow-up above left two holes. A mark is itself a repository file: an author who commits one `package.json` or `pyvenv.cfg` next to first-party code got the whole directory listed unread, so a route there gave exit 0 with every class covered (the open part of #213; #255 tester M1). And a run with by-design files read `covered` with nothing beside it. A first fix (#255, closed) tested every file of a marked tree for Flask and Express route words; it was per-language code, and the language-agnostic direction (#265) drops that.

| Option | Pros | Cons |
|---|---|---|
| A. A mark vouches for its tree only when git tracks nothing in it; a by-design count beside the coverage in text, Markdown and SARIF | Language-neutral; a package manager's install is never committed, and anything the author commits is read; no schema or exit-code change | Needs a readable git index at the scan root; without one, vendor trees are read and the run may be incomplete |
| B. Test each marked file for route words before skipping it (#255) | Works without git | Per-language code that must follow every extractor and spelling; removed with the static code (#265) |
| C. Parse every vendor file | Simplest rule | Real trees have files over the 1 MiB cap or that the grammar cannot parse, so nearly every project with installed dependencies would exit 4 |
| D. Accept forged marks as a residual | No code | Keeps a one-file bypass of `gates.pr` |

**Decision:** option A.

- **A tree is installed, and its files `vendor` unread, only when both hold.** Its package manager's mark is a regular file with exactly that name in a directory listing (`node_modules/<pkg>/package.json`, `node_modules/@scope/<pkg>/package.json`, `venv/pyvenv.cfg`, `.venv/pyvenv.cfg`; a stat would match `PACKAGE.JSON` on Windows and macOS, and a linked mark proves nothing). And the root `.git/index` tracks nothing in the tree, the tree itself, or a path above it (a submodule, whose own commits may hold the tree). This is decided by file identity, not by name: the file system can resolve a tracked name into the tree under another spelling, such as an NTFS 8.3 short name (`node_m~1/evil/app.js` lands in `node_modules/evil/` on Windows, #267 tester H1), another case on Windows or macOS, NTFS trailing dots and spaces, or another Unicode form on macOS. So every tracked path, and every directory above one, at the tree's depth is resolved on disk and compared with the tree (`os.SameFile`; an alias never changes a path's depth), and so is every tracked entry at the depth of a directory above the tree. A tracked name that cannot be resolved, for any reason but its absence, counts as tracking the tree; an absent one holds no file. Two name guards run first: tracked paths are compared with case folded and trailing dots and spaces dropped, and a tree whose path is not ASCII is never installed. The comparison walks down from the root, since an alias resolves component by component: a directory is compared only with the tracked names under the aliases of its parent. More than 4,096 such names count as tracked (fail closed), so the cost is at most 4,096 comparisons per installed tree and per directory above one, and each tracked name is resolved once (`BenchmarkTrackedIndexTracks`: 20,000 tracked directories and 300 packages in about 40 ms on Windows).
- **Anything else is read like first-party code**, under the follow-up rules above: a route there is extracted and evaluated, and a file static cannot read is a gap (exit 4). That covers a committed mark, a file committed into an installed tree, a tree in a submodule, and every scan without a git index creep can read whole: no `.git` directory at the scan root (a subdirectory scan, a tarball, a worktree whose `.git` is a file), an index over 64 MiB, a split or sparse index (extensions `link`, `sdir`), and an index written without a checksum (`index.skipHash`).
- **The index is read, never trusted blindly.** creep never runs git. It reads index versions 2, 3 and 4 with SHA-1 or SHA-256 checksums (`internal/gitindex`, a leaf package fuzzed on its own: `FuzzParse`). The checksum must match and picks the hash length, an extension git requires readers to understand is refused, and paths are capped at 4 KiB each and 128 MiB in all, so a crafted version 4 index cannot expand. A mistake can only make more trees read.
- **An installed tree vouches for all its files, whatever their language.** Real installs ship C extensions (`markupsafe/_speedups.c`), addon sources (`bcrypt`) and build helpers in other languages (`node-gyp`'s `Find-VisualStudio.cs`). The per-language limits of the follow-up guarded forged marks, which are now read anyway.
- **Go and PHP marks vouch for nothing.** `go mod vendor` output is committed by design, and `composer.json` is the project's own manifest, not a mark an install leaves. Go and PHP files under `vendor/` are `unsupported_language` (exit 4), like first-party Go or PHP.
- **A clean run names what it left out.** `report.ByDesignSummary` counts the listed files whose reason is by design (`report.SkipReason.ByDesign`: `vendor`, `generated`, `minified`), in that order, with counts and reason IDs only, never a path. The text summary prints `coverage excludes N files left out by design (vendor a, generated b, minified c), listed above`; Markdown prints a bold `No class covers the N files left out by design (…)` under the class table; SARIF adds a `creep/by-design` note to the invocation's notifications. Nothing is printed when no file was left out by design. The CLI decides incompleteness with the same `ByDesign` method, so the count and the rule cannot drift. The JSON report and its schema do not change.

Residual: the git index is the evidence, so a `.git` directory that came with the scanned tree, rather than one a checkout wrote, is trusted like a mark was: an archive with a crafted index can list first-party code under a mark as `vendor`. The file is still listed and counted beside the coverage. In CI the index comes from the checkout of the commit under review, which the author of a pull request cannot write. Code a CI step writes into an installed tree before the scan is not committed and counts as installed. That covers an install script, and also a plain install from a manifest the author controls: a `file:` or git dependency in `package.json`, or a local path or VCS requirement for pip, installs the author's code as a package with no script run (#267 tester I1). A step that runs the author's code can already change the gate's result. A first-party file that imports such a package by name is an unknown non-relative import, so its routes are marked partial.

## Amendment: the scan deadline (#260)

Nothing bounded a whole scan: a file crafted to wake every redaction rule takes minutes (`redact.MaxFileBytes`), a parse up to 30 s, and a hostile repository can hold many of them, so a CI job hung until its runner killed it, with no report.

**Decision:** `budget.max_seconds` (default 7200, 1 to 86400; the project file may only lower it, like the other limits) is the scan deadline. It starts after the tool canary and calibration, which read no repository text, and covers static analysis, redaction, the reader's model calls and the optional scanners (and discovery from ADR 0017 step D). When it passes, the redactor and the parser stop inside the file they are on and return no partial output; nothing more is read from disk. Every source file the walk had not reached, and every file the reader's slicer had not reached (including files static parsed when the deadline passed before slicing), is listed as `budget` with its hypotheses; only the file being redacted when the deadline passed is listed by the reader as `redact_failed`, its hypotheses `file_not_scanned`; every hypothesis not yet answered is `budget`. Past the deadline the installed-tree check (#213) proves nothing, so it neither reads the git index nor stats a tree, and a file under an installed tree is listed like first-party code (fail closed). An optional scanner the deadline cut, or that was still to run when it passed, is listed `failed` in the scanners section, as any scanner that did not finish. A walk the deadline cut before any route was extracted is not a `no_routes` run: the text and Markdown reports do not say the repository has no routes. The reports are written, stderr names the deadline, and the run is incomplete with reason `budget` (an early stop), exit 4. `creep estimate` reads and redacts the repository the same way, so the same deadline bounds it (ADR 0011): a cut estimate prints `PARTIAL ESTIMATE` and exits 4.

Replaying a recording the deadline cut is still incomplete (exit 4), but its reasons can differ: the recording holds only the answers given before the deadline, and it does not record that a deadline cut the rest, so the calls it lacks fail in replay as `send_failed`, not `budget`. A time limit cannot replay exactly; recording the cut would need a new state-line field, which is not worth it for a run that is incomplete either way. Report v1 does not change: the deadline is the run's time budget, so it reuses `budget` rather than adding a reason.

[ADR 0017](0017-language-agnostic-analysis.md) (accepted 2026-11-19) makes analysis language-agnostic. Tripwire candidates from such a file are still planned. The reasons that stop being emitted stay valid in the schema. The inventory appears only in the text and Markdown reports. Anything new in JSON needs report v2 and its own ADR.
- The by-design follow-up (P4, #213) keeps its evidence rules. Its "parsed without errors and holds no route" becomes "read in full by discovery with no candidate (no sink and no proposed entry)". The #207 residual (an unrecognised framework next to a recognised one) is addressed from step D, since discovery reads every source file whatever its framework (within ADR 0017's accepted residuals); it does not land with ADR 0012's language kits, which will not be built.

## Amendment: a directory link is not_regular (#214)

The walk never follows a link, but it listed one only when its name was a source name, so `web -> /outside` (a symbolic link, or a junction on Windows) left nothing in the report and the run could read as covered. **Decision:** a link or special file is also listed, whatever its name, when it may be a directory the walk does not reach at its own path. Once the walk is over, each symbolic link's target is read once (`os.Root.Readlink`, never followed) and followed over the names the walk reached, never by the file system: from the link's directory, `..` goes to the parent of a walked directory and every other name must be a walked child, so no step passes through another link. The link is not listed when that lands on a walked directory or regular file: pnpm's and npm or yarn workspaces' relative `node_modules/<pkg>` links and a venv's `lib64 -> lib` keep a run clean on Unix. It is listed when the target is absolute, empty, leaves the root, passes through another link, names the root's `.git` or `.creep` (never walked), anything the walk did not reach, or has more than 256 names. Any other reparse point (Go's `ModeIrregular`) gets one confined `Stat`, its panic recovered: a Windows junction, which the root refuses since its target is absolute, and anything that stats as a directory or fails is listed; pnpm and npm make junctions on Windows, so such a tree there ends incomplete. One that stats as a regular file, such as a OneDrive placeholder, keeps the rule for files: listed only when named as source. A FIFO, socket or device is not a directory and is listed only when named as source, as before. Past the scan deadline (#260) no link is read and every one that may be a directory is listed. A listed link is `not_regular`, exactly like a linked source file: not by design, because creep cannot say what it holds, so the run is incomplete (exit 4); in an installed tree (the #213 amendment) it is `vendor` like the tree's files. The root's `.git` and `.creep` are skipped whatever their type, so a link or junction there is not listed and a worktree's `.git` file, which holds a local absolute path, is never sent to discovery. Report v1 does not change. This replaces ADR 0017's note that directory links are not listed.

Why names, not `os.Root.Stat`: on Windows, Go 1.27.4's `os.Root` panics when it follows some relative links in a subdirectory (`real\web -> ..\real`, index out of range in `os.doInRoot`; no Go issue found on 2026-11-20), so a crafted repository crashed the scan, and climbing a target with `Stat` cost O(depth²) per link (2,000 links 250 levels deep took 6.5 minutes past a 2 s deadline). Each link now costs one readlink and at most 256 map lookups (`BenchmarkWalkLinks`: 2,000 links 120 levels deep, each with a 240-name target, from about 0.3 s to 1.3 s on the machines measured), and the installed-tree check (#213), which still stats tracked names, turns such a panic into an error and counts the tree as tracked (fail closed). Residual: a link the file system would resolve inside the repository but the names do not (an absolute target, a target through another link, a name in another case on Windows or macOS) is listed (exit 4) though the walk covers its target; checkouts store links as written, and a portable one is relative.

## Amendment: the sandbox's verification outcome (#23)

#23 wires the offline app build (ADR 0016 amendment) into `creep scan`: with `sandbox.enabled` and a usable runtime, the scan builds the app once after the analysis, and a missing, refused or failed build must show as `verification unavailable` with its closed reason, without failing the scan. Two questions are this ADR's: where the outcome goes in the report, and whether it moves the exit code.

| Option | Pros | Cons |
|---|---|---|
| A. Text, Markdown and SARIF only; JSON v1 unchanged | Follows the rule above (v0.1.0 is released, so v1 gains no field); every other format shows the reason, as with discovery's inventory (ADR 0017 D3) | A JSON consumer cannot read the reason; it sees only the finding statuses |
| B. A `run.verification` object in JSON v1 | Every format carries it | Breaks the rule above: fields are added only with a `schema_version` bump |
| C. The reason in each probable finding's `reason` | No schema change | `reason` means why a not-evaluated finding was not decided; `creep why` and gate consumers would read verification as a gap |

**Decision:** option A.

- `report.Verification` (`json:"-"`) holds a status and IDs only: `app_built`, or `unavailable` with a reason and an optional detail. The reasons are the sandbox's build reasons (`no_build_file`, `compose_refused`, `dockerfile_refused`, `context_refused`, `base_image_missing`, `build_failed`, `build_timeout`, `image_refused`, `runtime_error`, and `mirror_refused` since [ADR 0029](0029-build-mirror.md)) and the scan's own: `no_runtime`, `not_checked`, `sandbox_error` (the sandbox did not open, or the run was aborted), `interrupted` (Ctrl+C during the build) and `budget` (the scan deadline passed before or during the build). `report.New` refuses any other shape, any reason outside this closed set (`report.ValidVerificationReason`; a CLI test checks every `sandbox.BuildReasons` value is in it) and a detail that is not an ID; the CLI drops such a detail and turns an unknown reason into `sandbox_error`, so no sandbox answer can fail the scan.
- The text summary prints `sandbox: verification unavailable (<reason>[: <detail>]); findings stay probable`, or that the app was built offline and PoC verification is not built yet; with another `--format` the line goes to stderr. Markdown adds a Verification section and SARIF a `creep/verification/<status>` note. With `sandbox.enabled` false nothing is printed, and every report is as before.
- **The outcome never changes the exit code and never makes a run incomplete.** Without verification a finding stays `probable`, which is what a run without a sandbox reports (ADR 0007). A build failure that made the run incomplete would let a repository force exit 4 with a broken Dockerfile, and would make `sandbox.enabled` change results. So the build runs after the scan deadline's timer is disarmed, under its own context that ends at the same deadline: a slow build is `budget` here and never cuts the analysis.

JSON v1 and its schema stay unchanged, by the maintainer's decision on #278 (2026-11-20). A JSON consumer reads the sandbox's effect only through finding statuses (`verified` once PoCs exist, #24, #25); the reason stays in text, Markdown and SARIF.

## Amendment (#209, 2026-11-21): a lost report keeps the result, and `why` reads only a real `.creep`

A repository could commit `.creep/report.md/x`, a non-empty directory that cannot be removed. The rule above ("a name that cannot be removed exits 2") then ended every scan with exit 2 before any model call, with no summary and no incomplete mark. **Decision:** removing stale reports and writing them no longer stop the run. A report name that cannot be removed or written is skipped, and the formats that can be written still are. The result is still printed: the text summary or the report on stdout, and the incomplete mark. Each lost file is then named on stderr (`creep scan: reports: …`, escaped). The run keeps its own exit code (1 for a gate breach, 4 for an incomplete run). A run that would exit 0 exits 2 instead, so a lost report never reads as clean. A planted directory under a format `report.formats` does not list also exits 2, because a pipeline may upload `.creep/report.sarif` whatever the run wrote. The reports go through the directory handle that the state store checked when it opened `.creep` (not a link, not writable by others), never through `.creep` opened again by path.

A run that fails after opening its state (exit 2 or 3) also names, after its error, each stale report it could not remove, since that file is still on disk.

`creep why` opens `.creep` through the state store's own checks (`state.OpenExisting`, which never creates it) and exits 2 when they refuse it: a link, a Windows junction, a file, a directory others can write, or a `.creep` swapped for another directory between its `Lstat` and its open (the two must be the same file). It still reads `report.json` without blocking on a FIFO. A `report.json` that git tracks is still read: `scan` removes it before its next run, and `report.ReadJSON` and escaping already bound what it can print. A git index check would not close this, since the same file can come in an archive with no index; telling this user's report from a planted one would need a signed report, which report v1 does not have.

The text summary also changes. A probable or verified finding from a partial slice is listed with `partial slice`. The incomplete mark counts gaps (files and sinks not evaluated, partial verdicts) apart from what was left out by design (vendor, generated and minified files, tier S's `low_risk` skips): `N not evaluated or partial, M left out by design`. Report v1 does not change.

## Amendment: PoC rates and `creep reproduce` (#25, ADR 0020)

[ADR 0020](0020-poc-repetitions-and-bundle.md) runs each PoC 5 times from `creep scan` and adds `creep reproduce <id>`. For this ADR: a PoC that verified in 5 of 5 runs makes its finding `verified`; one that verified in 1 to 4 makes it `verified` with its rate, marked intermittent; one that verified in none leaves the finding `probable`, since the scanned repository builds the app and could otherwise discard its own finding. The rate follows the #23 decision above: it is in the text summary (`verified in 3/5 runs, intermittent` after the finding), in Markdown's notes and in SARIF (the result message and the `poc_verified_runs` and `poc_runs` properties), and **JSON v1 does not change** (`report.Finding.PoC` is `json:"-"`), so a JSON consumer reads `verified`. The verification summary counts the PoCs that ran, verified in every run, were intermittent, were not reproduced and were not run; `no_port` and `start_failed` join the closed reasons. The outcome still never makes a run incomplete; only `verified`, as the gate reads it, can move the exit code. `creep reproduce <id>` exits 0 when the PoC verified in at least one run, 1 when in none, 2 for usage, configuration or a missing or refused bundle, 3 for the sandbox (ADR 0007 codes, where 1 means the PoC did not reproduce).

## Amendment (#26, 2026-11-21): incremental scans with `--changed`

A pull request scan must finish in minutes, so #26 asks for a scan of what changed: `--diff <ref>` for the files changed since a ref and `--changed` for uncommitted changes before a commit. creep never runs git (product `os/exec` is allowed only in `internal/gateway`, `internal/scanrun` and `internal/sandbox`), so three questions are this ADR's: where the changed files come from, how a scan that skipped files stays honest about them, and what the report says.

| Option | Pros | Cons |
|---|---|---|
| A. `--changed <file>`: a list of paths the operator builds with git (`git diff --name-only -z <base>...HEAD` in CI, `git diff --cached --name-only -z` in a pre-commit hook) | No git code in creep; one input serves CI and pre-commit; the list only filters the walk | The operator runs git; a wrong list scans the wrong scope (the report shows it) |
| B. `--diff <ref>`, reading `.git` with the standard library | One flag, no list file | Resolving a ref needs loose and packed refs, commit and tree objects, pack indexes and delta chains: `compress/zlib` exists, the rest is several hundred lines of hostile-input parsing to fuzz, for a repository whose `.git` is untrusted (TB1); a shallow CI clone often lacks the base commit anyway |
| C. Run `git` | Least code | Breaks the exec rule (`make budget`), and the scanned repository's `.git/config` can name programs git runs (`core.fsmonitor`, `diff.external`) |
| D. Compare the working tree with the index (`internal/gitindex` and blob hashes) | No list | Sees unstaged changes only: misses the staged ones a pre-commit hook checks and every committed change of a pull request |

**Decision:** option A. Both cases of the issue's scope are one input: CI passes the files changed since the base, a hook the staged ones. The issue's criteria name neither flag, and A meets them with the least code.

- **`--changed <file>`** limits `scan` and `estimate`; any other command exits 2 with it, and so does an empty value. The file is opened as `--config` is (a regular file, no FIFO, no UNC share, nothing under `/proc`, `/sys` or `/dev`), read whole, at most 16 MiB, before the state directory or any model call. It holds one path per line (LF or CRLF), or one per NUL when it holds a NUL (git's `-z`). Blank entries are skipped and repeats count once; a repeat is skipped before it is copied, and a list at the cap of distinct short paths parses in about a second and 250 MB (`BenchmarkParseChangedList`). An entry over 4,096 bytes, an entry git quoted (it quotes unusual names unless given `-z`, and the quoted form would miss the real file) and one `report.ValidPath` refuses (absolute, a drive letter, a backslash, a `..`, `.` or empty segment) fail the whole scan with exit 2, naming the entry escaped: a list creep cannot read exactly would scan a scope nobody chose.
- **The list only filters the walk.** The walk runs as in a full scan: links never followed, the root `.git` and `.creep` skipped, installed trees proven, refused names listed. A walked regular file the list names goes to discovery; names match without regard to case, because on a case-insensitive file system (Windows, macOS) git's index can spell a name otherwise than the disk, and scanning a file more never hides a change. A listed path that is no such file (deleted, a directory, a link, under the root `.git` or `.creep`) is only counted. No entry is opened, joined into a path or compared with anything but the names the walk produced, so a list cannot make creep read outside the root, or read anything a full scan would not.
- **Unchanged files are listed, by design.** Every other walked file that could be source (`discover.MaybeSource`) is listed with the new reason `unchanged`, which is by design like `vendor` (`report.SkipReason.ByDesign`): listed, counted beside the coverage (`coverage excludes N files left out by design (unchanged N)`), and not a gap. The walk's own gaps stay, and so does every gap of a listed file: a link, a refused name, or a changed file discovery could not read in full makes the run incomplete (exit 4) exactly as in a full scan. An incremental exit 0 means the listed files are clean, never that the repository is.
- **Every format marks the scope.** The text summary (on stderr with another `--format`), Markdown (a banner under the run status) and SARIF (a `creep/incremental` note) print `incremental scan (--changed): N listed files scanned, M listed paths are no file creep reads (…); K unchanged files not evaluated (reason unchanged), and code they hold that a changed file reaches is not evaluated either`, with counts only. `creep estimate --changed` measures only the listed files and prints the same line.
- **Report v1 gains one enum value**, `unchanged` in `coverage.not_evaluated[].reason`, and nothing else: the counts stay out of JSON (`Report.Incremental` is `json:"-"`), and the files themselves say what was skipped. Maintainer decision on #26: there is no report v2, and v1 changes additively only (an optional field or a new enum value, never a removed or retyped field). This replaces the rule in Consequences ("from the first release on, report fields change only with a `schema_version` bump") and ADR 0017 D3's "JSON stays v1 and gains nothing". Why the value is additive: only a run the operator started with `--changed` emits it, so a consumer that never passes the flag sees no change; and a consumer that switches on the reasons it knows and treats any other as a gap reads an incremental run as not clean, which fails safe. A consumer that refuses unknown enum values (a validator holding the v0.1.0 schema, or `creep why` of v0.1.0, whose `report.ReadJSON` refuses an unknown reason) must accept `unchanged` before it reads an incremental report. `docs/schemas/report-v1.json` says the same in its description.
- **Reach is per file.** Discovery proposes entry points and sinks within one file, and every candidate is planned at worst case, so the hypotheses of a changed file are exactly the ones a full scan plans there (`TestScanChangedEvaluatesOnlyListedFiles` compares both), and a changed sink outside every changed entry point is still planned on its file-level route. **Known limit:** creep has no cross-file graph (ADR 0017), so a flow from a changed file into a sink in an unchanged file, or from an unchanged route through an unchanged helper into changed code, is not evaluated; the mark says so, and a full scan (the nightly gate, #28) covers it.
- Optional scanners still scan the whole tree, and the sandbox builds the app from every walked file, so an incremental run builds the same app.
- `--diff <ref>` is out of the product (maintainer decision on #26, 2026-11-21): creep has no such flag and no git-object reader. The caller produces the list, for example `git diff --name-only -z origin/main > changed.txt`. The Action (#29) builds the list from the event's base commit, must keep exit 4 failing the job, and the baseline (#27) must not read the missing findings of an `unchanged` file as fixed.

Residual: the list is the operator's input. One that names the wrong files scans the wrong scope; the report then lists every unchanged file and counts the listed paths it found no file for, so a typo shows. Names are compared byte for byte after lower-casing, so a name the disk stores in another Unicode normalization than git's index (NFD on macOS against NFC) still misses its file and is counted as a listed path creep found no file for.

## Amendment: baseline and accepted risks (#27, ADR 0022)

[ADR 0022](0022-baseline-and-accepted-risks.md) adds `--baseline <file>`, `--baseline-write` and `creep accept <id>`. For this ADR: the **Gate** rule above skips a probable or verified finding a live baseline entry suppresses, and nothing else changes in how a run is judged. A suppressed finding keeps its status and is listed in every format; a `not_evaluated` finding is never suppressed; the incompleteness rules and exit 4 do not read suppressions, so a baseline never turns an incomplete run into exit 0 or 1. Report v1 gains two optional finding fields under the additive rule of the #26 amendment: `fingerprint` (32 lowercase hex digits, on probable and verified findings) and `suppression` (`kind` `baseline` or `accepted`, `expires`, and an accepted risk's `reason`); `report.ReadJSON` checks them as `report.New` does, so `creep why` and `creep accept` refuse a planted report that suppresses anything else. The text summary, Markdown and SARIF also print how the baseline was used (suppressed findings by kind, expired entries, entries that matched no finding); those counts are not JSON (`Report.Baseline` is `json:"-"`). A baseline file that cannot be read exits 2 before the run opens state; a refused or failed `--baseline-write` never exits 0.

## Amendment: a gate per scan mode (#28, ADR 0021)

[ADR 0021](0021-gate-per-mode.md) adds `--mode pr|nightly` (nightly also for a GitHub Actions `schedule` event). For this ADR: the **Gate** rule above reads the gate of the scan's mode, `gates.pr` for a pr scan, `gates.nightly` and `gates.pr` for a nightly one, with the same class severities, and exit 1 means one of them tripped; a nightly scan never passes what a pr scan fails. A pr scan never builds the app or runs a PoC, even with `sandbox.enabled`, so the #23 and #25 amendments apply to nightly scans only. The verification outcome still never makes a run incomplete and JSON v1 does not change, but in a nightly scan it decides which status the gate reads: when the sandbox is off, verification is unavailable or a PoC candidate got no completed run, `gates.nightly` is read with its status raised to probable (`verified:high` as `probable:high`), so a finding nothing verified fails the run at the gate's severity instead of passing it (the gate failure path, not exit 4). Each scan prints the mode and its gate on stderr (`gate: ...`).

## Amendment: discovery stability (#37, ADR 0024)

[ADR 0024](0024-discovery-stability.md) adds `--stability <n>` (1 to 5, scan and estimate). For this ADR: report v1 gains one optional finding field under the additive rule of the #26 amendment, `stability` (`runs` 2 to 5, `seen` 0 to `runs`, `unstable` true when `seen < runs`), only on a probable or verified finding; `report.ReadJSON` checks it as `report.New` does. Text, `creep why`, Markdown and SARIF print the label (`unstable discovery: seen in 2 of 3 runs`), which never shares a word with an intermittent PoC (`verified in 3/5 runs, intermittent`, ADR 0020). The gate, the incompleteness rules and the exit codes do not read it.
