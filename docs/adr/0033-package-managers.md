# ADR 0033: Homebrew tap and Scoop bucket as release channels

- **Status:** Proposed
- **Date:** 2026-11-24
- **Deciders:** @Ludocius
- **Changes:** the release contract gains two channels, a Homebrew cask in `sneakercreepers/homebrew-tap` and a Scoop manifest in `sneakercreepers/scoop-bucket`, both written only by the release workflow from the release's own archives; one new secret, `PACKAGE_REPOS_TOKEN`, in the `release` environment; one new script, `.github/scripts/package-repos.sh`. No Go dependency, package, flag or exit code.
- **Fitness function:** the row "The tap and bucket token reaches only the push step" of [architecture.md §9](../architecture.md#9-fitness-functions) (`internal/tools/budget/package_token_test.go:TestPackageReposTokenOnlyInPushStep`), `internal/tools/releasescripts` (the push script publishes nothing without the token, for a prerelease, for a pin that is not exactly an archive of the tag in `checksums.txt`, or for a downgrade) and the release workflow's `dry-run` job (the real cask and manifest pin the archives in `checksums.txt`; the cask keeps the quarantine hook)
- **Threat model:** TB12 and P1 to P5 ([threat-model.md §4.11](../threat-model.md#411-package-managers-344-adr-0033))

## Context

#344: creep ships as signed GitHub release archives (cosign keyless over `checksums.txt`, an SPDX SBOM per archive, build provenance) and through `go install`. Comparable tools grow through package managers. `homebrew-core` needs notability first, so a project-owned tap and bucket come first. Both must be generated by the release workflow from the same signed and attested archives and pin each archive's sha256.

The maintainer created both repositories (public, default branch `main`, a ruleset blocking deletion and force-push, direct pushes allowed). Deploy keys are disabled at the org level, so the writer is a token.

## Options

| Option | Pros | Cons |
|---|---|---|
| A. goreleaser `brews` (a formula) published by goreleaser | One config; `test do` block | `brews` is deprecated since GoReleaser v2.10 and `goreleaser check` exits 2 on it (verified with the pinned v2.20.2), which would fail the `dry-run` job; goreleaser publishes during `goreleaser release`, before the workflow verifies the signature and provenance and while the release is still a draft, whose asset URLs are not public; the token would sit in the environment of the whole goreleaser process (syft, cosign, the Go toolchain) |
| B. goreleaser `homebrew_casks` and `scoops` published by goreleaser, `skip_upload` templated on the token | Upload code is goreleaser's | Same ordering and exposure problems as A |
| **C. goreleaser writes the cask and the manifest into `dist/` only (`skip_upload: true`); a script pushes both after the release is verified and public** | The tap and bucket never name a draft or unverified asset; the token reaches one small step; a missing token is one warning line | About 120 lines of bash that `internal/tools/releasescripts` tests with a fake `gh` |
| D. Generate a formula from our own template | A real formula with `test do` | Re-implements what goreleaser maintains; drifts from Homebrew |

## Decision

Option C.

1. **Generation.** `.goreleaser.yaml` declares `homebrew_casks` (name `creep`, binary `creep`, homepage, description, macOS and Linux, amd64 and arm64) and `scoops` (name `creep`, homepage, license `Apache-2.0`, description, Windows amd64 and arm64), both `skip_upload: true` and without a token. goreleaser writes `dist/homebrew/Casks/creep.rb` and `dist/scoop/creep.json`, each pinning the sha256 of the archive it names, the same bytes `checksums.txt` lists and cosign signs. A cask, not a formula, because GoReleaser deprecated formulas for prebuilt binaries; a cask has no `license` or `test do` stanza, so the cask carries neither. The macOS binaries are not notarized by Apple, so the cask clears the quarantine attribute on the installed binary after brew has checked the archive's sha256 (goreleaser's documented `install_steps` hook).
2. **Publishing.** The release job uploads the cask and the manifest as the run artifact `package-manifests`. A separate `package-repos` job (`needs: release`, `release` environment, `contents: read`) runs on a fresh runner that never ran goreleaser, syft or the Go toolchain (v0.5 release review R1): it downloads the artifact, downloads `checksums.txt` and its bundle from the published release, `cosign verify-blob`s them with the release identity, and only then runs `.github/scripts/package-repos.sh "$GITHUB_REF_NAME" dist` with `PACKAGE_REPOS_TOKEN` in that step's env only. The script puts `Casks/creep.rb` in the tap and `bucket/creep.json` in the bucket on `main` through the GitHub contents API, committer `creep-release <noreply@github.com>`, message `creep <tag>`; anyone with the token can set that committer, so reviewers match a commit to a release workflow run, not to the name (the API's own committer is not used because GitHub documents signed API commits only for apps and bots). It publishes nothing and logs a `::warning::` when the token is empty, and a `::notice::` for a prerelease tag (one with `-`), so a release candidate never reaches users of the tap or bucket; the release still succeeds in both cases. Before the token is used, the script checks that each cask `url`/`sha256` and manifest `url`/`hash` pair is a line of the verified `checksums.txt`, that every URL is an asset of the tag's release, that `version` is the tag without `v`, and that the pins are exactly the darwin and linux (cask) or windows (manifest) archives `checksums.txt` lists, so no count is hard-coded. It then reads the version the tap and the bucket hold and refuses both pushes unless the new tag is strictly higher (`sort -V`); a missing file is a first publish and a file that already holds exactly this release is skipped. Every tag release shares the concurrency group `release`. A missing generated file, a pin mismatch, a downgrade or a failed API call (an expired or revoked token) fails the job after the release is already public. The release stays valid; the tap and bucket keep the previous version. Recovery: regenerate the token if needed (same name, same two repositories, Contents read and write), store it with `gh secret set PACKAGE_REPOS_TOKEN --env release`, and re-run the `package-repos` job within the artifact's 7 days; a partial publish (tap pushed, bucket failed) is finished the same way, since the re-run skips the file that already holds the release. After 7 days, let the next release update them. The token expires at most a year after creation; the maintainer regenerates it before it expires.
3. **The token.** A fine-grained personal access token with **Contents: read and write** on `sneakercreepers/homebrew-tap` and `sneakercreepers/scoop-bucket` only, no other permission, stored as the secret `PACKAGE_REPOS_TOKEN` of the protected `release` environment (maintainer approval, `v*` tags only; `.github/settings/release-environment.json`). No PR, nightly or bench workflow names it (`TestPackageReposTokenOnlyInPushStep`). Secrets cannot be read back through the API, so `make repo-settings-check` does not compare it; the environment policy it compares already limits who can use it.
4. **What the channels verify.** brew and scoop check only the sha256 the cask or manifest pins. They do not run cosign or `gh attestation verify`. The sha256 values come from the release job, which verified the signature and provenance of those same archives before publishing, so a user who trusts the tap and bucket gets the verified bytes; a user who does not verifies the installed archive with the commands in [SECURITY.md](../../SECURITY.md#verifying-a-release), which the README keeps recommending.
5. **Deferred.** `homebrew-core` needs notability (stars, downloads, a stable release history) and builds from source with its own review; it is revisited once creep qualifies. winget needs a manifest pull request to `microsoft/winget-pkgs` per release, under Microsoft's review and a token with write access to a fork, a wider grant than this ADR wants before there is demand; it is revisited with `homebrew-core`.

## Consequences

- `brew install sneakercreepers/tap/creep` (macOS and Linux) and `scoop bucket add sneakercreepers https://github.com/sneakercreepers/scoop-bucket && scoop install creep` (Windows) install the latest release.
- Until the maintainer stores `PACKAGE_REPOS_TOKEN`, every release logs the warning and leaves the tap and bucket as they are.
- Anyone with the token, or with write access to the tap or bucket, can point the cask or manifest at other bytes with a matching sha256; brew and scoop would install them. Mitigations and residual risk: threat model P1 to P5.
- A goreleaser bump re-runs `goreleaser check` and the `dry-run` job's cask and manifest checks on the release PR.
- The quarantine hook uses goreleaser v2.20's `install_steps` form, which renders a `postflight_steps` block with Homebrew's `{{staged_path}}` token (the `dry-run` job checks the cask keeps `postflight`, `on_macos` and `staged_path}}/creep`); it is checked on the first real install on macOS, and changed with goreleaser if Homebrew refuses it.
