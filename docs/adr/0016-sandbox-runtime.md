# ADR 0016: Drive Docker or Podman through their CLI from one package

- **Status:** Accepted (maintainer approval 2026-11-19)
- **Date:** 2026-11-19
- **Deciders:** @Ludocius
- **Amended by:** [ADR 0019](0019-poc-templates.md) (Accepted (maintainer, 2026-11-21): the PoC runner, after the canary, and the database marker lookup join the run network; the app gets one read-only mount, creep's canary file); [ADR 0029](0029-build-mirror.md) (Proposed: an operator-provided internal mirror network for rootless Podman builds, `sandbox.mirror.*`)
- **Changes:** the exec rule in `internal/tools/budget` (one new package, `internal/sandbox`, matched exactly); the layers table (`sandbox` moves to layer 5 and imports `static`; `verify` and `mcp` move to 6, `cli` to 7, `cmd/creep` to 8); the CLI contract (`creep clean`, the sandbox section of `creep doctor`, one stderr line in `creep scan` when `sandbox.enabled`)

## Context

#21 needs a container runtime: PoCs are written by a model that read untrusted code, so they must run only in a container (AGENTS.md invariant 4), never on the host. The issue asks for Docker and Podman (rootless preferred) through their Docker-compatible API, a hardened profile for every container, per-run labels, cleanup on exit and Ctrl+C, `creep clean` for orphans, a synthetic `.env`, and never the Docker socket or host credentials inside a container. With no runtime, a scan must still succeed and findings stay `probable`.

Talking to a runtime collides with two rules:

- The Docker-compatible API is HTTP over a unix socket (`/var/run/docker.sock`, `$XDG_RUNTIME_DIR/podman/podman.sock`) or a Windows named pipe. Speaking it from creep needs `net` (and `net/http`), which only `internal/gateway` may import (invariant 1), and it is a connection to something that is not a model endpoint (invariant 5).
- Running the `docker` or `podman` CLI needs `os/exec`, which only `internal/gateway` (model CLIs, ADR 0014) and `internal/scanrun` (ADR 0013) may import.

Facts that shape the profile (from `docker run --help`, `podman run --help`, `docker info`, `podman info` and a Docker Desktop 29.7 check on the dev machine):

- Both CLIs take the same run options for everything the profile needs: `--network=none`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, `--read-only`, `--tmpfs`, `--user`, `--pids-limit`, `--memory`, `--memory-swap`, `--cpus`, `--ipc=private`, `--pull=never`, `--label`, `--mount=type=bind,...,readonly`.
- A tmpfs from `--tmpfs` is not world-writable unless it says `mode=1777`; a non-root user cannot write `/tmp` otherwise (found by the integration test).
- `docker info` reports `SecurityOptions` (`name=seccomp,profile=...`, `name=rootless`), `OSType`, `OperatingSystem` (`Docker Desktop`) and whether memory, pids and CPU limits work. `podman info` reports `host.security.rootless`, `host.security.seccompEnabled`, `host.serviceIsRemote` and `host.cgroupControllers`.
- The Docker CLI's endpoint comes from `DOCKER_HOST` or the current context, and can be `tcp://` or `ssh://`. `docker context inspect --format '{{json .Endpoints.docker.Host}}'` prints it; `--host` pins it for one call.
- Killing `docker run` does not stop its container, so cleanup must remove containers by name or label.
- `docker run` adds the proxies of the client's `config.json` (credentials in the URL included) to every container's environment unless the variable is set explicitly; Podman copies the host's proxy variables unless `--http-proxy=false`.
- Docker 29 has `--use-api-socket`, which mounts the API socket into the container.

## Options

| Option | Pros | Cons |
|---|---|---|
| A. Speak the API from `internal/gateway` over the socket | No CLI dependency; structured answers | The gateway becomes a container client as well as the model egress point; it opens a non-model connection (invariant 5); HTTP over a unix socket and a named pipe without `x/sys` or `unsafe` is new code in the most sensitive package |
| B. Speak the API from `internal/sandbox` with a `net` reach exception | Gateway untouched | Breaks invariant 1 for a second package; the exception would cover `net` in general, not only the runtime socket |
| C. `internal/sandbox` runs the docker or podman CLI through `os/exec`, matched exactly like `scanrun`; one fixed argv builder per call; no `net`, no socket opened by creep | No network code outside the gateway; the exec exception is one package wide, as for scanrun; the CLI already handles contexts, rootless sockets and Docker Desktop's pipe | Depends on CLI flags and their output formats; the CLI is the operator's program, so its plugins and telemetry are outside creep's control |

## Decision

Option C. What decided it: it is the narrowest exception. creep opens no socket and imports no `net`; the only new power is starting two known programs with arguments only this package builds, the same shape `scanrun` was approved with.

**Which binary.** `exec.LookPath` finds `docker` and `podman` as the OS would; `exec.ErrDot` (current directory, relative entry) is refused, and the match must pass `static.OutsideRepo` (final path, links and junctions followed, compared with the repository and the working directory by file identity, ADR 0013). On Windows only an `.exe` runs. `sandbox` imports `static` for that check, so it moves to layer 5 beside `scanrun`; `verify`, which imports `sandbox`, moves to 6, and so do `mcp` (to stay below `cli`), `cli` to 7 and `cmd/creep` to 8.

**Which endpoint.** Docker: `DOCKER_HOST` if set, else the endpoint of `DOCKER_CONTEXT` (a plain name only) or the current context. Only a `unix://` socket at an absolute path and a named pipe on this machine (`npipe:////./pipe/<name>`; a pipe on another host is a UNC path opened over SMB) are accepted, and every later call passes it as `--host`; `DOCKER_HOST` itself is never passed to the CLI. Podman runs locally only: outside Linux, or with `CONTAINER_HOST` or `CONTAINER_CONNECTION` set, it is refused without being started; every Podman call carries `--remote=false`; a service that still reports `serviceIsRemote` is refused. No `tcp://`, `ssh://` or remote connection is ever used.

**Which runtime is usable.** Linux containers, seccomp on and not unconfined, and memory, pids and CPU limits available. Isolation is `rootless` (Docker rootless or Podman rootless), `vm` (Docker Desktop: the daemon runs in a VM) or `rootful`; detection checks the configured runtime (`sandbox.runtime`) first and picks the strongest isolation, the configured one on a tie. A rootful daemon is usable, and `creep doctor` warns about it.

**How the CLI runs.** `exec.CommandContext` with the final path and arguments from fixed builders (`context inspect`, `info`, `image inspect`, `run`, `ps`, `rm`); no shell. The environment is fixed: `PATH` without relative entries or entries in the repository or working directory (Podman finds `conmon` on it), the home and XDG directories, `DBUS_SESSION_BUS_ADDRESS`, `DOCKER_CONFIG`, the Windows start-up variables, `DOCKER_CLI_HINTS=false` and `LC_ALL=C`; no keys, tokens, proxies or `DOCKER_HOST`. The operator's `DOCKER_CONFIG` is kept for detection (the current context) and for `creep clean`, which starts no container; an open sandbox's CLI (`image inspect`, `run`, and the `ps` and `rm` of its own cleanup) gets an empty `DOCKER_CONFIG` in the work directory, since the endpoint is already pinned. Every container also gets each proxy variable set empty (both cases), Podman `--http-proxy=false`, and a spec cannot set a proxy variable. The working directory is the temp directory, stdin is empty, stderr goes to the null device (it carries container output too), stdout is capped (1 MiB), and a timeout plus a two-second wait delay bound every call. Answers are decoded into closed structs; container lists become `rm` arguments only as hex IDs.

**The hardened profile.** One builder makes every `run` command line: `--rm`, `--name=creep-<run>-<n>`, `--pull=never`, `--network=none`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, `--read-only`, `--tmpfs=/tmp:rw,noexec,nosuid,nodev,size=64m,mode=1777`, `--user=65534:65534`, `--pids-limit=128`, `--memory=512m`, `--memory-swap=512m`, `--cpus=1`, `--ipc=private`, `--log-driver=none` (the attached CLI still reads stdout, capped; the runtime keeps no log file, which nothing would bound), each proxy variable set empty (Podman also `--http-proxy=false`), the labels `io.github.sneakercreepers.creep.managed=true`, `io.github.sneakercreepers.creep.run=<run ID>` and `io.github.sneakercreepers.creep.container=<name>`, then the spec's env as `--env=NAME=value` (checked names, no line breaks; a bare name, which would copy the host's value, cannot be written), its mounts, the image and its command. The values are constants, not config: nothing may loosen them. The image must be pinned (`name@sha256:<hex>` or a local `sha256:<hex>` ID) and present; pulling is a separate, later step. Before each run, `image inspect` reads the image's declared volumes, and an image with any `VOLUME` is refused: the runtime would back each one with a writable anonymous volume on the host, past `--read-only`. A failed or unreadable answer also starts nothing. The image is pinned by digest, so the image inspected is the image that runs. Seccomp is the runtime's default profile, required at detection; creep ships no profile of its own. Each container has a timeout (default 1 minute, at most 10).

**Mounts and the synthetic `.env`.** A mount is a read-only bind of one regular file below the sandbox's own work directory (`os.MkdirTemp`, 0700), with no link, junction, socket or device on the way, and no runtime socket name (`docker.sock`, `podman.sock`, `/run`, `/var/run`, Windows pipes) or credential name (`.ssh`, `.aws`, `.docker`, `.kube`, `.gnupg`, `.netrc`, `.git-credentials`, `gcloud`, creep's state) anywhere in the path, before or after links resolve. `--volume`, `--env-file` and `--use-api-socket` are never built. `WriteSyntheticEnv` writes a `.env` with a random `creep-synthetic-…` value per name for an app under test to read instead of a real one.

**Cleanup.** A timeout, Ctrl+C (caught only while a container runs, so the container is removed and `Run` returns `ErrInterrupted`) a canceled run or a refused start removes the container by its run label and a per-container label carrying its name, never by name alone (a name conflict may be another program's container); `Close` removes the run's containers by label and the work directory; `creep clean` removes every creep-labeled container on every reachable local runtime. A creep that is killed leaves its containers until `creep clean`.

**CLI.** `creep doctor` lists each runtime (path escaped, reason as an ID) and the one a scan would use with its rootless status and isolation; a missing runtime is not an error. `creep clean` exits 0 when every reachable runtime was cleaned (or none is reachable) and 3 when a removal failed. `creep scan` with `sandbox.enabled` prints one line saying whether a runtime was found; nothing is verified until #22, so findings stay `probable` and the exit code is unchanged. `sandbox.*` stays an operator-only setting (the project file cannot set it).

## Consequences

- `internal/tools/budget` gains `internal/sandbox` in `execAllowedExact` (no subpackages); `net`, `net/http` and `syscall` stay forbidden there, and tests pin all three (`imports_test.go`).
- Protection tests in `make protections`: `TestEveryContainerIsHardened` (every `run` line holds the profile and nothing outside an allowlist), `TestHardeningCheckCatchesWeakenedRun` (the check fails on each weakened line), `TestMountRefusesHostPaths`, `TestRunRefusesImageVolumes`, `TestOperatorProxiesNeverReachContainers` (the operator's `config.json` proxies never reach `run`, and the broken path is caught). The integration tests (`integration_test.go`) run a probe built from `testdata/probe` inside a real container and kill a child creep to prove `creep clean` removes the orphan; they run once per usable runtime (Docker and Podman alike) and skip where none is usable, except in CI on Linux, which sets `CREEP_REQUIRE_SANDBOX=1` so a skip fails. The probe also fails when the environment holds anything beyond the spec's and the runtime's own variables, when a proxy variable is non-empty, or when a pids, memory or CPU limit cannot be read.
- Residual risks (threat model §4.6): a rootful daemon is allowed with a warning; a kernel or runtime escape is out of creep's hands; the CLI's plugins and telemetry belong to the operator; `creep clean` also removes the containers of a run in progress; podman machine (macOS, Windows) is unsupported until a later issue shows its connection is local; a Podman `containers.conf` `env` entry is the operator's own setting and still reaches containers.
- #22–#25 build on this package: an internal network (`--internal`, labeled and cleaned the same way), image builds that leave the repository's `.env*` files out, pulls by digest only. Each needs its own review of the arguments it adds.
- If the CLIs change flag names, `run` fails (exit 125) and the container is removed; no weaker command is tried.

## Amendment: run network, synthetic database and network canary (#22)

- **Status:** Accepted amendment (maintainer approval on #264, 2026-11-19)
- **Date:** 2026-11-19
- **Changes:** the argv builders of `internal/sandbox` (`network create`, `network ls`, `network rm`; `run` with the run's network, a network alias, `--detach` and fixed extra tmpfs mounts); two digest-pinned images the operator pulls (creep still never pulls); the VOLUME rule (a VOLUME covered by one of the package's own tmpfs mounts is allowed); the `creep clean` output and the `creep doctor` sandbox section. No new dependency, no `net`, no socket, no new package; the exec exception stays one package wide.

### Context

#22 asks for one `--internal` network per run (`creep-<run>`) with no published ports and internal DNS only, a synthetic database seeded from the project's migrations with no host data, and a canary container that tries an external IP and a public DNS name before each PoC batch and aborts the run when it gets through. The decision above anticipated the network ("labeled and cleaned the same way") and asked for a review of every argument it adds. Three facts, checked on Docker Desktop 29.7, shape it:

- An `--internal` bridge still gets a gateway address in the daemon's network namespace, so the host (on Linux the host itself, on Docker Desktop its VM) can connect to every container on it. With `com.docker.network.bridge.inhibit_ipv4=true` the bridge has no address and nothing on the host reaches the containers. Podman's netavark keeps the gateway address on internal networks (aardvark-dns listens there) and has no such option; rootless Podman's networks live in the user's own namespace, which the host cannot reach.
- Docker before 26 forwarded public names from internal networks through the daemon (a DNS exfiltration path); Docker 26 and later do not. Whatever the version, only a probe from inside proves it.
- The official PostgreSQL image declares `VOLUME /var/lib/postgresql/data`, which the decision refuses. A tmpfs at that exact path replaces the anonymous volume, so nothing lands on the host. Its entry point runs as any user: as 65534, with `PGDATA` one level below the tmpfs, `initdb` creates a directory that user owns.

### Options

| Option | Pros | Cons |
|---|---|---|
| A. creep pulls the canary and database images by digest | Works out of the box | The daemon's pull is a network call creep triggers to something that is not a model endpoint (invariant 5); a new builder that reaches a registry |
| B. creep never pulls; two images pinned by digest in the code, the operator pulls them, `creep doctor` prints the exact command; a missing image makes the networked run fail closed | No new network path; the image that runs is the reviewed digest | One manual step per machine |
| C. Build the canary and database from the repository or the host | No registry at all | The build runs hostile build steps (#23's problem); a database built from the host's binaries is host data |

### Decision

Option B, the narrowest: nothing new reaches a registry, and every new argument comes from fixed builders.

**Images.** `CanaryImage` is BusyBox 1.37.0 and `DatabaseImage` PostgreSQL 17.12 on Alpine, both the multi-arch index digest under a fully qualified name (`docker.io/library/…@sha256:…`, so Podman never resolves a short name). `--pull=never` stays on every run; `creep doctor` reports each image present or missing, with the pull command for a missing one aimed at the endpoint creep checked: `docker --host=<endpoint> pull <ref>` (the bare `docker pull <ref>` when Docker has no pinned endpoint) or `podman --remote=false pull <ref>`, so the image lands on the engine that runs it. Changing a digest is a reviewed code change.

**Network.** `network create --driver=bridge --internal --ipv6=false [--opt=com.docker.network.bridge.inhibit_ipv4=true] --label=…managed=true --label=…run=<run> creep-<run>`, the option on Docker only. `--ipv6=false` overrides a daemon's default network options, so no address family escapes the canary. Rootful Podman gets no network (`ErrHostReachable`): its bridge address would let any local process reach the services. The network is created once per run, on first use; a name conflict (someone else's network) fails without touching it. Only a container started through `RunBatch` or `StartDatabase` joins it: the spec fields that pick the network, an alias, `--detach` and extra tmpfs mounts are unexported, so a caller cannot set them, and `Run` always uses `--network=none`. On the run network, `run` gets `--network=creep-<run>` in place of `--network=none` and, for the canary and the database, `--network-alias=<name>` (lower-case letters, digits, dashes). No `--publish`, `-p`, `-P`, `--expose`, `--dns`, `--add-host` or host network is ever built. `Close` and `creep clean` remove containers first, then the networks carrying the run's (or creep's) label, listed as hex IDs only, without `--force` (on Podman it would remove whatever container uses the network).

**Canary.** Before every `RunBatch` and before the database starts, a container of `CanaryImage` runs on the network with its own alias (`canary-<n>`, so a canary still being removed cannot answer for the next) and a fixed one-line script. It listens on a port of its own, then tries its own alias through the network's resolver and over TCP (controls, which must succeed), `example.com` through the network's resolver, `example.com` directly against `1.1.1.1` over UDP, and TCP to `1.1.1.1:443` and `8.8.8.8:53` (each must fail). It prints exactly one `key=yes|no` line per check. Any probe that succeeds is `ErrNetworkLeak`; a failed control, a missing, duplicate or unknown line, a non-zero exit, truncated output or a canary that did not run is `ErrCanary`. Either aborts the run for good: no container of that batch starts, and every later `Run`, `RunBatch` and `StartDatabase` returns the same error. The canary's knocks leave the machine only when isolation is already broken, which is what aborts the run.

**Database.** `StartDatabase(migrations)` writes the migrations, in the order given, into one `seed.sql` in the sandbox's work directory (at most 512 migrations, 1 MiB each, 8 MiB in all, no NUL byte; paths never enter the SQL; a `;` line after each), runs the canary, then starts `DatabaseImage` detached on the network as `db`, with the hardened profile plus `--tmpfs` at `/var/lib/postgresql/data` and `/var/run/postgresql` (`rw,noexec,nosuid,nodev,size=256m,mode=1777`), the seed as its only mount (read-only, at `/docker-entrypoint-initdb.d/seed.sql`, where the image's entry point runs it with `ON_ERROR_STOP`), `POSTGRES_USER`, `POSTGRES_DB` and `PGDATA` fixed and `POSTGRES_PASSWORD` a fresh `creep-synthetic-…` value. A client container polls `pg_isready` for at most 90 seconds; the server listens on the network only after the seed ran, so ready means seeded, and a failed migration is `ErrDatabase`. One database per run. `MigrationPaths` picks the migrations from the repository's file list: the `.sql` files directly in the first of `migrations/`, `db/migrations/`, `database/migrations/`, `sql/migrations/`, `supabase/migrations/` that has any (down migrations left out), else `prisma/migrations/*/migration.sql`, ordered with digit runs compared as numbers. The caller reads the files through its own repository reader (TB1).

**VOLUME rule.** An image VOLUME is still refused unless one of the package's own tmpfs mounts sits at exactly that path; only the database and its client containers have one.

**CLI.** `creep clean` prints the containers and networks it removed. `creep doctor` lists the two pinned images and how to pull a missing one. Scans are unchanged: PoC verification is #23–#25.

### Consequences

- New protection tests in `make protections`: `TestCanaryLeakAbortsRun` (each probe getting through, each failed control and each malformed answer aborts the run and starts no PoC), `TestNoPortPublished` (no command line of a whole run publishes a port or uses the host network, the network command line is pinned, rootful Podman gets no network, and each weakened line is caught), `TestDatabaseMountsNoHostPath` (the database mounts only the seed from the work directory, its data is tmpfs, its credentials synthetic, the seed holds only the migrations, and each weakened line is caught). `TestEveryContainerIsHardened` now covers the canary, the database, its poll and batch PoCs. Integration tests (once per usable runtime, required on CI Linux) pull the two images by digest and prove on a real engine that a PoC trying the internet fails while it reaches the database; `pg_dump` shows only the migration's table and row and no host data; no port is published and a container on the host's network cannot connect to the database; `Close` and `creep clean` remove the network; the canary reports a leak on a network that is not internal; and without `inhibit_ipv4` the host does reach the database (Docker Desktop, rootful Docker), so the host check can fail.
- Residual risks: the operator pulls the images (a registry or mirror they trust serves the pinned digest, or the run fails); the canary proves egress for its probes only, not every address or port (a firewall that lets only some destinations through is out of its sight), and the network's own resolver answers locally even when it does not forward, so its probe catches a resolver that resolves but not one that forwards while its upstream is down (any reply from `1.1.1.1` asked directly does count as a leak); the host-side bridge keeps an IPv6 link-local address, while `--ipv6=false` leaves each container's interface without IPv6; the seed is a bind mount, so a migration can read its host path, and with it the operator's temp directory and often user name, from `/proc/self/mountinfo` (host metadata, not a secret; a seed without a host mount is left to a later issue); a migration runs as the database superuser inside the container (`COPY … FROM PROGRAM` runs there, on the internal network, with no capabilities); migrations of other tools (Rails, Django, Alembic, dbmate markers) or other SQL dialects are not run or fail, so their tables are missing; rootful Podman runs no networked container.
- Still for #23–#25: the app container on this network, PoC templates, `verified` findings and the scan wiring that reads migrations through the scan's repository reader.

## Amendment: offline app build from the repository's own build files (#23)

- **Status:** Accepted (maintainer, 2026-11-20)
- **Date:** 2026-11-20
- **Changes:** the argv builders of `internal/sandbox` (`build`; `image ls` and `image rm` for the images it builds; `run` of a built image through `StartApp`); the `creep clean` output (images too); `internal/sandbox` now also reads YAML with the existing `go.yaml.in/yaml/v3` (ADR 0001). No new dependency, no `net`, no socket, no new package, no config key; the exec exception stays one package wide.

### Context

#23 asks to build the app only from what the repository provides (`compose.yaml`/`docker-compose.yml` or a `Dockerfile`, never a generated one), with registry access only through an allowlist proxy or a configured mirror, an offline mode for air-gapped machines, no network at run time, and a missing or failing build reported as `verification unavailable` without failing the scan. The threat model (§7) already named the hazard: a build runs the repository's own steps, so it is hostile code. Facts that shape the design (Docker with BuildKit, Podman with Buildah):

- `--network=none` on `docker build` or `podman build` binds RUN steps only. The builder itself still fetches what an instruction names: an `ADD` URL or git repository, every image in `FROM`, `COPY --from` and `RUN --mount=from=` that is not local, and a `# syntax=` frontend image. BuildKit prefers a local image for `FROM` (its default resolve mode); `podman build --pull=never` refuses a missing one.
- BuildKit's `--network` accepts only `default`, `none` and `host`; a user-defined network, where an allowlisting proxy could live, needs the legacy builder or a docker-container builder. An allowlist proxy on the default bridge is not an allowlist: a RUN step can ignore the proxy variables and connect directly.
- `docker compose build` interprets the whole compose file: `include`, `extends`, host variables, remote and out-of-repository contexts, `additional_contexts`, build `secrets`, `ssh`, `network: host`, `extra_hosts`, `privileged`, `entitlements`. The Docker CLI also turns its `config.json` proxies into build arguments.
- BuildKit has no per-build memory, pids or CPU limit with the default docker driver, and writes layers to the daemon's disk.

### Options

| Option | Pros | Cons |
|---|---|---|
| A. Run `docker compose build` or `docker build` on the repository | Every project builds as its authors intended | The compose file chooses networks, secrets, host paths and privileges; the context is the repository itself (links, `.env`) |
| B. A build network with an allowlisting proxy container creep runs | Dependencies install | A third pinned image with egress; BuildKit cannot use the network; creep would own a proxy's allowlist (invariant 5) |
| C. Offline only: creep reads the build file itself, checks it, stages a copy of the context and runs one fixed `build` command line with `--network=none` and only local base images; a mirror or proxy mode waits for a design the builder can enforce | Nothing new reaches a network; every argument is creep's; air-gapped machines work by default | A project whose build downloads dependencies is `verification unavailable` until they are vendored or baked into a local base image |

### Decision

Option C for this slice. What decided it: it is the only option where "a build that tries a non-allowlisted host fails" is enforced by the engine and not by a proxy's good behaviour, and it adds no network path. The registry allowlist or mirror waits for its own decision (Consequences).

**Build file.** Only root files: the first of `compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`, else `Dockerfile`, else `Containerfile`, each a clean path in the scan's file list, read through the scan's repository reader (TB1), at most 256 KiB. creep never runs `docker compose` and never writes a Dockerfile. From a compose file it takes the one service with a `build` section (none: a root Dockerfile, if any; several: refused) and from it only `context`, `dockerfile` and `target`; `labels`, `tags`, `no_cache` and `pull` are ignored, and any other build key (`args`, `secrets`, `ssh`, `network`, `extra_hosts`, `additional_contexts`, `cache_from`, `cache_to`, `privileged`, `entitlements`, `dockerfile_inline`, `platforms`, …) refuses the file, as do a top-level `include`, the service's `extends`, YAML merge keys, and a context or Dockerfile that is not a plain string naming a path inside the repository (absolute, `..`, a backslash, a colon, a `$` variable, a URL or git remote), with the Dockerfile inside the context. A service's runtime settings (`privileged`, `network_mode`, `pid`, `cap_add`, `devices`, `volumes`, `ports`, `extra_hosts`, `env_file`, external networks) are never read, so they reach no command line: the app runs only with the hardened profile.

**Dockerfile check.** An allowlist, not a list of bad forms: creep accepts only a lexical form that it and BuildKit read alike, and refuses everything else. A first version listed bad forms, and the #274 tester got past it with BuildKit's own parser: a BOM or a `//` before `syntax=`, `\v`, `\f` or a lone `\r` as the separator after a keyword, and `From=` or a quoted `from=` in a mount.
- Bytes: only printable ASCII, tab and line feed are accepted, plus a carriage return right before a line feed, which BuildKit's line scanner drops too. So there is no BOM, no `\v`, `\f`, lone `\r` or non-ASCII, and the only white space in a line is the space and tab both readers split on.
- Directives: none in any form, anywhere in the file. A `# key=` comment in any case or spacing, a `//` line, or a file starting with `{` (the JSON form) refuses the file. So no frontend image is named, and `\` is the only escape character. A plain comment like `# PATH=...` is refused too; that costs some files and loosens nothing.
- Keywords and flags: matched in any case. `FROM` may carry only `--platform`, and only `$BUILDPLATFORM` or `$TARGETPLATFORM`. `RUN` may carry only `--mount`, so `--network`, `--security`, `--device` and any unknown flag are refused in every spelling. `COPY` may carry only `--from`, `--chown`, `--chmod`, `--link`, `--parents` and `--exclude`; `ADD` only `--chown`, `--chmod`, `--link` and `--exclude`. `--link` and `--parents` may stand alone, as BuildKit reads them. A flag with a quote or a backslash in it is refused. `ONBUILD` is refused: BuildKit runs a stage's triggers in a later `FROM` of that stage, and the app build needs none. Mount keys are read in any case. A mount may only be of type `bind` (the default) or `tmpfs`, which leave nothing behind and read only the staged context or an earlier stage. A `cache` mount outlives `--no-cache`, `Close` and `creep clean`, and is keyed by its target, so the operator's later builds would read what a hostile build wrote; `secret` and `ssh` read the host. A `from=` is checked like `COPY --from`, and a `source=` above its root is refused.
- `ADD`: a URL, git remote (scp-like too) or variable source is refused.
- Fail closed (v0.2 Dockerfile re-check, which proved each of these with BuildKit's and Buildah's own parsers and with Docker 29.7): only BuildKit's instructions are read, `ONBUILD` aside, and an instruction without a flag list takes no flag. A line ending in two backslashes is refused, since Buildah (Podman) continues it and BuildKit does not. An exec form must be a valid JSON array of strings, an `ADD` source only a plain path's characters (no `:`, `@`, `#`, variable, quote or escape), a `--mount` only the bind and tmpfs keys with no variable. An `ARG` that could set `BUILDPLATFORM` or `TARGETPLATFORM` is refused: a global `ARG` replaces the builder's value, and Docker fetched a foreign platform's layers for `FROM --platform=$BUILDPLATFORM`. Before the first `FROM`, an `ARG` must be one bare name, since the builder reads global `ARG`s itself (`SOURCE_DATE_EPOCH` can name a stage whose remote `ADD` BuildKit fetches) and `FROM` takes no variable. A Dockerfile whose name ends in `.in` is refused: Buildah runs cpp(1) over it, so a `#define` the check reads as a comment can turn a local `ADD` into a remote one, and `#include` reads host files (PR #308 review). The build gets the checked bytes: a staged Dockerfile that differs from them is refused.
- Stage references: a stage counts only when it names an earlier stage. `FROM` names one by its exact lower-case name only. `--from` names one by name or by an index below the number of earlier stages; `from=` by name only, since BuildKit reads `from=0` as the image `docker.io/library/0`. A stage name BuildKit refuses, or one given twice, is refused.
- Image IDs: a reference `image inspect` could read as an image ID or ID prefix (hex only, or `sha256:` and hex) is refused. Inspect found a local image for `FROM 526f`, and the build then pulled `docker.io/library/526f`.
- Images: every other reference is an image, and must be present locally (`image inspect`) before the build starts. A missing one is `base_image_missing`, and nothing is pulled. The presence check reads the whole inspect answer. An image with `ONBUILD` triggers, or an answer that is not JSON, is `image_refused` (`base_onbuild`). Docker shows triggers as `Config.OnBuild`. Podman's inspect has no such field, but its `History` lists the step that set each one (`created_by` holding `ONBUILD`, any case), which buildah would still run. An image whose `Os`/`Architecture` differ from the engine's is `image_refused` (`base_platform`): BuildKit would fetch the native variant. The engine's platform is read once per build in a fixed format (`docker version --format {{.Server.Os}}/{{.Server.Arch}}`, `podman info --format {{.Host.OS}}/{{.Host.Arch}}`), and an unreadable answer is `runtime_error`. The variant is not compared, since neither engine reports its own. A variable in an image, more than 16 images, or no `FROM` is refused.
- Heredoc bodies are read as instructions too, which refuses more, never less.

A fuzz target compares the check with an independent model of BuildKit's lexer, which splits on `[\t\v\f\r ]+`, strips a BOM, reads both directive styles and lower-cases mount keys. Nothing the check accepts may hold a directive, a RUN network option, or an image it did not return.

Engine backstops:
- Docker: `--pull=false` still pulls a missing image, so the presence check is the control. BuildKit refuses `RUN --network=host` without the `network.host` entitlement, which creep never grants. No `docker build` option pins the built-in frontend: the `BUILDKIT_SYNTAX` build argument forwards to a frontend image just as the directive does, so creep passes no build argument, and the directive refusal is the only control.
- Podman: `--pull=never` refuses a missing image, and buildah has no frontend directive. buildah may honour a per-step `RUN --network` without an entitlement, so the check refuses that flag on both engines.

**Context.** The builder never sees the repository: the context's files are copied, through the scan's reader, into a fresh `build-<n>` directory in the sandbox's 0700 work directory, every directory and file created new (no link followed). Left out: every name starting with `.env` (the synthetic `.env` replaces them at run time), `.git`, `.creep`, and credential files (`.ssh`, `.aws`, `.azure`, `.kube`, `.gnupg`, `.netrc`, `_netrc`, `.git-credentials`, `.npmrc`, `.pypirc`). At most 20 000 files and 512 MiB; an unreadable file refuses the build. A file that starts with `#!` or an ELF header is written executable (the file list carries no mode).

**Build command line.** One builder: the pinned endpoint (`--host=<endpoint>` or `--remote=false`), `build --quiet --network=none --no-cache --iidfile=<work>/iid-<n> --file=<staged Dockerfile> --label=…managed=true --label=…run=<run>`, then Docker's `--pull=false` or Podman's `--pull=never --http-proxy=false --layers=false --force-rm`, an optional `--target=<checked stage>`, and the staged context. No `--build-arg`, `--secret`, `--ssh`, `--allow`, `--add-host`, `--build-context`, `--cache-from`, `--cache-to`, `--output`, `--push`, `--platform` or `--tag` is ever built. The CLI runs with the open sandbox's empty `DOCKER_CONFIG` (no `config.json` proxy becomes a build argument, and the default builder is used), its fixed environment and a 15-minute timeout; Ctrl+C or the timeout kills the CLI, which cancels the build. The image ID comes from the iidfile, not from output a RUN step could print. The built image goes through the VOLUME check every image gets; one that declares a `VOLUME` is `image_refused`.

**Result.** `Build` returns an `App`: the image ID, or a closed reason (`no_build_file`, `compose_refused`, `dockerfile_refused`, `context_refused`, `base_image_missing`, `build_failed`, `build_timeout`, `image_refused`, `runtime_error`) and a closed detail (a known compose key, a Dockerfile rule, `exit_<n>`), never repository text. Only Ctrl+C, the caller's cancel and an aborted run return an error, so a build failure cannot fail a scan.

**Run phase.** `StartApp` starts only an image this sandbox built, once per run, after the canary passed, detached on the run's `--internal` network as `app`, with the hardened profile; nothing is published. `Close` removes the run's containers, then the images labeled with its run ID (untagged ones included, `image ls --all`) and the IDs `Build` recorded (the CI runner's Docker left the untagged build out of its labeled listing, found by `TestRealBuildIsOffline`), then its network; `creep clean` also removes every creep-labeled image. Images are removed by hex ID, without `--force`.

### Consequences

- New protection tests in `make protections`: `TestBuildIsOffline` (Docker and Podman build lines hold the offline options and nothing outside an allowlist, endpoint pinned), `TestBuildCheckCatchesWeakenedBuild` (each weakened line is caught), `TestBuildRefusesEscapes` (each hostile compose file or Dockerfile starts no build and is unavailable, not an error; a compose file's runtime settings reach no command line), `TestBuildContextLeavesSecretsOut` (the staged context holds no `.env`, git, creep or credential file and nothing outside the repository, and the check catches one that does). `TestEveryContainerIsHardened` and `TestNoPortPublished` now cover the built app. `TestBuildThroughRealExec` proves the build reads an empty `DOCKER_CONFIG` through the real exec path. `TestRealBuildIsOffline` (once per usable runtime, required on CI Linux) builds from the pinned BusyBox: `.env` is not in the image, a RUN step that reaches for a public address fails the build, a missing base image is not pulled, and `Close` removes the image.
- Residual risks: build steps run with the builder's defaults, not the run profile (root in the build container, default capabilities, no creep memory, pids or CPU limit, layers on the daemon's disk), bounded only by the timeout, so a hostile build can use CPU, memory and disk until then; a killed Podman build may leave a build container that only `buildah` lists; local base images are the operator's, and one with `ONBUILD` triggers is refused (Docker's `Config.OnBuild`, Podman's `History`), except a Podman image whose history was squashed or stripped, which hides the step that set a trigger while buildah still runs it; the platform check does not compare the variant; with Docker, BuildKit may look up a present base image's tag in its registry (a digest-pinned `FROM` needs no lookup), a request the daemon makes that carries the image name only; the daemon's build cache stays (`--no-cache` keeps builds from reusing it); a build that downloads dependencies is unavailable offline.
- Maintainer decisions (2026-11-20): v0.2 builds offline only. The registry allowlist or mirror mode moves to a v0.3 issue (for example an operator-provided internal network the canary checks plus a configured mirror URL, applied only to the build and set only from user or policy config, like `sandbox.*`; it needs a builder that honours a user-defined network). A follow-up PR for #23 closes it: it wires `Build` into the scan (`verification unavailable` and its reason in the report, under ADR 0009's report contract) and adds Dockerfiles to `testdata/apps`, with the test-app guard adjusted to allow them. Delivered there: `creep scan` builds through `internal/cli/verify.go` (the report side is ADR 0009's amendment on the verification outcome), and each test app has one shared Dockerfile from the pinned BusyBox that copies its files, since an offline build cannot install their frameworks.
- Left for later, each with a decision first: build arguments from an allowlist, and compose files with several builds.

## Amendment: minimum engine versions and engine-escape refusals (final v0.2 release pentest)

- **Status:** Accepted (maintainer, 2026-11-22)
- **Date:** 2026-11-22
- **Changes:** detection (two new closed reasons, `old_runtime` and `unknown_version`, shown by `creep doctor`; a Docker runtime now also answers `docker version --format {{json .Server}}` through the pinned endpoint); the Dockerfile check (rules `container_path`, `mount_from`, `transport`); the Podman `build` command line (memory and CPU limits); the app's `run` command line (`--workdir`); a built image whose working directory is refused is `image_refused` (`workdir`). No new dependency, network path, package or config key.

### Context

The release pentest at 1d8a78b found three escapes the Dockerfile check accepted because only a patched engine blocks them, while creep set no minimum engine version: `WORKDIR /proc/self/fd/8` then `RUN cd ../../..` (runc < 1.1.12, CVE-2024-21626; the WORKDIR also stays in the image `StartApp` runs), a bind mount `from=` a stage holding `ln -s / /l` (Buildah < 1.35.3, CVE-2024-1753, the host's root, read-write with `rw`), and mount targets through links (BuildKit < 0.12.5, CVE-2024-23652). A link a RUN step makes is invisible to a lexical check, so the engine version is the control; the check can only refuse the plain forms. It also found no resource limit on the build, and `FROM containers-storage:alpine` passing the image-name rule.

### Decision

- **Minimum versions, a user-visible requirement.** A runtime is usable only with Docker Engine >= 25.0.2 (it embeds BuildKit 0.12.5; the sandbox's empty `DOCKER_CONFIG` selects no other buildx builder) whose default runtime is runc >= 1.1.12, or Podman with Buildah >= 1.35.3 and runc >= 1.1.12 or crun >= 1.4.4. Versions come from what the runtimes report offline: `docker version --format {{json .Server}}` (components `Engine` and `runc`) with `docker info`'s `DefaultRuntime`, and `podman info`'s `host.buildahVersion` and `host.ociRuntime`. Below a minimum is `old_runtime`; missing, unparsable, duplicated, or another OCI runtime is `unknown_version`. Either makes the runtime unusable: a scan reports `no_runtime` and builds nothing, `creep reproduce` exits 3 (ADR 0007), and `creep doctor` names the reason. A distribution backport to an older version is refused; that costs some hosts and loosens nothing.
- **Dockerfile check.** A `WORKDIR` and a mount `target`, `dst` or `destination` must be a plain path that, cleaned of `..`, does not climb above its directory and does not start in `/proc`, `/sys` or `/dev`; a relative path is read as if from `/`, since the previous working directory may be `/` (`container_path`). `RUN --mount` `from=` is refused for stages and images alike (`mount_from`): the staged context, which holds no link, is all a bind mount gets. An image reference with a containers/image transport prefix, or any `://`, is refused (`transport`).
- **App working directory.** After the build, creep reads the image's `Config.WorkingDir`; it must be a clean absolute path the same rule accepts, else `image_refused` (`workdir`). `StartApp` passes it as an explicit `--workdir` (`/` when unset), and refuses an `App` without a checked one.
- **Build limits.** Podman builds get `--memory=2g --memory-swap=2g --cpu-period=100000 --cpu-quota=200000`. Docker gets none: BuildKit ignores the legacy `--memory` and `--cpu-*` flags, and buildx's `--resource` is too recent to rely on. Neither builder has a pids limit flag. Both stay bounded by the 15-minute build timeout.

### Consequences

- Operators on older engines lose verification until they upgrade; findings stay `probable`, and scans still succeed.
- Dockerfiles that bind-mount from another stage are refused; `COPY --from` still works.
- New protection tests: `TestRuntimeMinimums`, `TestEngineEscapesRefused`, `TestAppWorkdirChecked`, `TestStartAppNeedsCheckedWorkdir`; the fuzz oracle also reads the new rules. Threat model X22.
- Not verified against a live Podman here (none on the development machine); the field names follow `podman info --format json`.
