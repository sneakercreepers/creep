# ADR 0015: Model CLI presets as embedded data

- **Status:** Accepted (maintainer approval on PR #227, 2026-11-16)
- **Date:** 2026-11-16
- **Deciders:** @Ludocius

## Context

#6 ([ADR 0014](0014-command-model-through-gateway.md)) lets any CLI be the model through `model.run`. Each CLI needs its own non-interactive and tools-off flags (`claude -p --tools "" --strict-mcp-config`, `codex exec --sandbox read-only`, ...), and those flags change with CLI releases. A wrong flag gives a model that reads untrusted code a shell. #7 asks for presets: `model: { preset: claude-code }` resolves the command, presets are community data that need no code change, and every preset passes the tool canary. This adds a config key (`model.preset`), a public contract.

## Options

| Option | Pros | Cons |
|---|---|---|
| A. Presets embedded in the binary (`go:embed`), closed YAML schema, resolved in `internal/config` into `model.run` | Nothing on disk to plant or swap; reviewed like code (CODEOWNERS); one path to the gateway (`model.run`), so the #6 checks and the canary apply unchanged; `config explain` shows the command | A new or fixed preset needs a release |
| B. Presets loaded from a user directory (`~/.creep/presets`) or the repository | New CLIs without a release | A file the scanned repository or another local user can plant chooses the program; needs a trust and pinning scheme like recipes (`creep.lock`) |
| C. Preset as a new contract in `internal/models` | Could pass argv without re-quoting | Second path to the gateway beside `model.run`; duplicates #6's checks |

## Decision

A. Presets are embedded data in `internal/presets` (layer 0, no internal imports), resolved by `internal/config` after every layer has applied: the preset fills `model.run` (quoted for the gateway's shell-free splitter) and `contract: command`, and `config explain` names the preset as their source. The deciding reason: a preset picks the program that reads scanned code, so it must not come from anywhere the repository can write.

Rules: the schema is closed (unknown or duplicate keys, a second document, a program that is a path, args as a shell string, control characters are errors); `tools_off` lists every argument run that switches tools off and each must appear in `args` (empty only with `no_tools: true`); `model.preset` and `model.contract` cannot be set in the project file; `model.name` cannot come from the project file when the preset passes it to the CLI (`{model}`), and never starts with `-`; a preset next to `model.run` or a non-command contract is an error, never a silent choice; a policy lock on `model.run`, `model.contract` (unless locked to `command`) or `model.preset` binds even when it pins the default, so a preset that would change the locked key is a config error (exit 2). The tool canary still runs on every preset at `creep doctor` and every scan start.

**Host reads.** The canary sees files written and commands that leave files, never reads. So every preset declares `host_reads: none` (no tool can read outside the empty working directory: `claude-code` with `--tools ""` and no MCP, `ollama run`) or `host_reads: unbounded` with a one-line `host_reads_detail`. `codex` is unbounded: `codex exec` runs shell commands without approval, and `--sandbox read-only` blocks writes and network but not reads, so injected code can make it read `~/.ssh` or `~/.aws` and put the content in a prompt to its provider, past creep's redaction. No codex flag that confines reads to the working directory is documented, so none is set. `gemini` is unbounded: read-only built-in tools (read_file, glob, web fetch, `google_web_search`, which also reaches the web outside creep's gateway) and MCP servers from `~/.gemini/settings.json` may stay enabled in headless mode. `creep doctor` and every scan print an escaped warning for an unbounded preset before the canary runs. This qualifies ADR 0014's "Reading is bounded: the working directory is empty", which holds only for CLIs with no read tools.

**Verified.** Only Claude Code can be checked by hand by the maintainer, so every preset also states `verified: true|false` (required). `verified: true` means a maintainer saw the manual canary check (CONTRIBUTING.md) pass with the real CLI, reported through the Model preset issue form; `claude-code` is `true`, `gemini`, `codex` and `ollama` are `false` until a contributor reports the check. `creep doctor` and every scan print one escaped warning line for a preset that is unverified, reads the host, or both; the automatic canary still runs on every scan.

## Consequences

- Adding or fixing a preset is a data-only PR (`internal/presets/<name>.yaml`) with the manual canary check from CONTRIBUTING.md; `TestEmbeddedPresets` validates every file in `make check` and CI.
- A CLI flag change needs a creep release. Users can still write `model.run` themselves meanwhile.
- `internal/presets` is a CODEOWNERS path; review checks each flag against the CLI's documentation.
- Residual (threat model §4.2a C6): a CLI's own settings (hooks, MCP servers, read-only tools) are outside the preset; the canary catches writes and commands, not reads. `codex` and `gemini` are `host_reads: unbounded` and warn at every run; for untrusted code the docs recommend `claude-code` or `ollama`. A codex or gemini flag that confines reads would let a later preset change move them to `none`.

## Amendment (#229, 2026-11-19)

Follow-ups from the #227 review; the decision above stands.

- **gemini trust.** Gemini CLI exits 55 in headless mode in an untrusted folder, so the preset adds `--skip-trust`, which trusts the working directory for that session only (not saved; [trusted folders](https://geminicli.com/docs/cli/trusted-folders/)). The directory is the fresh, empty directory creep makes for each call, so the workspace files trust would load (`.gemini/settings.json`, `.env`, `GEMINI.md`, custom commands) cannot exist there. Trust does let user-level MCP servers connect, so the preset also passes `--allowed-mcp-server-names creep-no-mcp-server`, an allowlist with a name nobody defines. What stays outside the preset: tools, policies and include directories from `~/.gemini/settings.json`, and two files Gemini reads above its working directory: the first `.env` up the tree, and `GEMINI.md` files up to a `.git` it finds. On a shared machine another user could plant them in `/tmp`, so the gateway now makes each call's directory under `<user cache>/creep/model` instead of the system temp directory, and refuses to run unless every directory from it up to the home directory (or the volume root) is a real directory others cannot write to ([ADR 0014](0014-command-model-through-gateway.md) amendment); empty `.env`, `.gemini/.env` and `.git` stop files in each run root end Gemini's env and `GEMINI.md` searches there, so neither `~/.env` nor a file planted above home is read. `host_reads` stays `unbounded`. In headless mode the default policy denies `web_fetch`, and `google_web_search` sends its query to Google, the provider, so the warning's "send them to its provider" holds unless the user's own settings or policies allow more. A personal Google login is refused server-side in this mode, so the preset needs `GEMINI_API_KEY` (an AI Studio key) declared in `model.env`. A planted `.env` cannot replace that key, because Gemini loads only variables that are not already set.
- **codex reads.** `codex exec` now gets `--ignore-user-config` (no MCP servers, tools or sandbox settings from `~/.codex/config.toml`) `-c features.shell_tool=false` (no command execution tools) and `-c features.view_image=false` (no tool that opens local images), all documented, plus `-c project_root_markers=[]`, which per the advanced config guide skips the parent-directory search and treats the working directory as the project root, so no `AGENTS.md` or `.codex/` above it is read. Still read: the login and the global `~/.codex/AGENTS.md` under `CODEX_HOME`, the operator's own files. The canary cannot prove a read path is closed, and these flags are not yet checked with the real CLI, so `host_reads` stays `unbounded` until a maintainer's manual check confirms them. The API key variable is `CODEX_API_KEY`.
- **verified reset.** `TestVerifiedPresetsArePinned` pins a length-prefixed SHA-256 of `program` and `args` for each `verified: true` preset. Changing either fails `make check` until the PR sets `verified: false` and removes the pin, so the reset no longer depends on review.
- **Flag confidence.** codex `--ephemeral` is documented in the non-interactive guide. gemini `--extensions none` disables every extension in Gemini CLI's extension enablement code. The new flags above are medium confidence until the manual check runs; an unknown flag makes the CLI fail, so the canary fails closed (exit 3). A renamed config key behind `-c` could instead be ignored silently, which is one more reason codex stays `unbounded`.
- **No antigravity preset (#258).** Google moved Google AI Pro and Ultra from Gemini CLI to Antigravity CLI (`agy`) on 2026-06-18, so the `gemini` preset is API-key only. Antigravity CLI's [headless](https://www.antigravity.google/docs/cli/headless), CLI reference, permissions and settings documentation lists no flag that switches off its file, shell, browser or MCP tools, plugins or skills, no flag that pins the permission mode (`--mode` takes only `accept-edits`, `auto` or `plan`; `--dangerously-skip-permissions` only loosens it), and no way to skip or replace the user settings file (`~/.gemini/antigravity-cli/settings.json`), whose `permissions.allow`, `toolPermission` and `agentMode` decide what runs. In headless mode it soft-denies tools that would ask and still exits 0. `--sandbox` does not change this: it runs shell commands inside an OS isolation boundary (sensitive files such as `~/.ssh` blocked, writes to the workspace and temp directories, no network unless allowed), but file, browser and MCP tools stay governed by the permission settings, and where the sandbox is unavailable (for example Windows before 11 24H2) the flag silently has no effect. Stdin input exists only as `--input-format stream-json` (NDJSON messages), not the plain-text prompt the command contract sends. A preset must switch tools off with its own flags (`tools_off`), and here the user's settings, not the preset, would decide, so creep ships no `antigravity` preset. Revisit when Antigravity CLI documents flags that disable tools or ignore user settings.

## Amendment (#272, 2026-11-22)

- **Status:** Proposed (needs maintainer approval on the #272 PR)

- **codex check.** The codex preset was run by hand with codex-cli 0.171.0, logged in with the operator's own account, in the gateway's empty private working directory with the gateway's argv and environment. Every flag and `-c` key exists (`codex exec --help`, `codex features list`). Prompts asked the model to read a canary file outside the working directory by absolute path, run `echo PROBE-<random>` and `whoami`, list the parent directory, do the same through a sub-agent, and search or open a web page; `--json` events showed every tool call. Shell, file read and directory listing never ran, and the canary token appeared in no output.
- **More tools off.** The #229 flags left web search and page open on (built-in `web_search`, and the ChatGPT app connectors of the `codex_apps` MCP server, which also include tools that publish pages and sites), plus image generation and plugin installs. The preset now adds `-c features.apps=false`, `-c features.plugins=false`, `-c features.image_generation=false` and `-c web_search=disabled`; with them the model reported no web tool and made no web call. Each removed tool was seen in the listing before the override and gone after it, and `-c web_search=disabled` alone still left a web search through `codex_apps`.
- **Still unbounded.** `apply_patch` has no documented switch and stays on. Its verification opens any absolute host path: a patch for a missing file fails with "Failed to read file", and one with a wrong context line fails with "Failed to find expected lines", so injected code can learn whether a file such as `~/.ssh/id_ed25519` exists and whether it holds a guessed line. No file content was printed, and under `--sandbox read-only` the model declined to write. A JavaScript code tool (`functions.exec`) stays on with no `require`, `Deno`, `import` or `fetch`; sub-agents inherit the same args; goal and clock tools are harmless. So `host_reads` stays `unbounded`, with a detail that names `apply_patch`.
- **Still unverified.** The CONTRIBUTING.md tools-on control (`codex exec --sandbox workspace-write --skip-git-repo-check -`) passed the canary instead of failing on Windows: codex reported the workspace read-only and ran no command, so it does not prove the canary would catch a codex with tools. `verified` stays `false` until a maintainer runs that control where workspace-write works (Linux or macOS) and the preset is pinned.
