# Threat model

What `creep` protects, from whom, where the trust boundaries are, and which control and test holds each one. It describes the code on `main` (v0.2.0 released, v0.3 in progress), not the roadmap: anything not built yet is marked **planned** with its issue, and §7 lists the requirements it must meet before it ships.

Review it:

- for every pull request that crosses a trust boundary (§2). The PR template has the checklist; CODEOWNERS covers the paths;
- in the release pentest and the per-version architecture review ([ADR 0004](adr/0004-pentester-per-release.md), [ADR 0005](adr/0005-auditor-architecture-review.md));
- in full at least once per major version.

Architecture and package responsibilities: [architecture.md](architecture.md). Package list: [map.md](map.md). Reporting a vulnerability: [SECURITY.md](../SECURITY.md).

## 1. Assets

| ID | Asset | Why it matters |
|---|---|---|
| A1 | Source code of the scanned repository | It leaves the machine only redacted, only to an endpoint the user allowlisted and consented to: the reader sends slices, and model discovery (ADR 0017 D1, #265) sends whole redacted source files to the same endpoints under the same consent, so a consent stored before #265 also covers them (R20) |
| A2 | Secrets and personal data inside that code | They must never reach a model endpoint unredacted |
| A3 | The model API key (`CREEP_API_KEY`) | Spend and account access |
| A4 | The user's machine | `creep` reads hostile input; it must never run it or let it choose what `creep` runs |
| A5 | Integrity of the result: findings, coverage, exit code | CI gates trust them; a run that missed work must never read as clean |
| A6 | The audit trail: `egress.log` and `payloads/` | The user's record of exactly what left the machine and where |
| A7 | Trust state outside the repository: the state secret (`<user config dir>/creep/state.key`), the consent store, the calibration cache | They decide which recordings, runs, consents and tiers are believed |
| A8 | The `creep` source, build and release | A compromised `creep` compromises every user |

## 2. Trust boundaries

```
              operator-trusted                 │            untrusted
                                               │
 flags · user file · --config · CREEP_POLICY   │   scanned repository: code, file names,
 CREEP_API_KEY · consent store · state.key ────┼──► creep.yaml, a planted .creep/      (TB1)
                                               │
 ┌──────────────────────── creep process ──────┼─────────────────────────────────────┐
 │ discover (TB2) ──► gateway: whole files     │                                     │
 │   │ IDs, enums and line spans               │                                     │
 │   ▼                                         │                                     │
 │ planner ◄── Signal (IDs, enums, numbers) ── reader ◄── redacted slices            │
 │  (no text)                       (TB3)      │  │                                  │
 │                                             │  ▼                                  │
 │ report ◄──────────────────────────── models ◄── gateway ◄── redact               │
 └──────┬──────────────────────────────────────┼──────┬──────────────────────────────┘
        ▼ (TB6)                                │      ▼ HTTPS, allowlisted (TB4)
  .creep/report.* · terminal · CI              │   model endpoint: its replies are
  · GitHub code scanning                       │   untrusted (TB5)
```

| ID | Boundary | What crosses it | Controls |
|---|---|---|---|
| TB1 | Scanned repository → `creep` | File contents and names, `creep.yaml`, whatever sits in `.creep/`, the root `.git/index` | Read through `os.Root`, regular files only, size caps, no FIFO blocking; `creep.yaml` must not be a link and is checked again after the open; `CREEP_POLICY` must be absolute; project config cannot choose where code goes, the model tier, the scanners, the sandbox or the report outputs, raise a limit, grant consent or loosen gates below the operator's; state is believed only with a valid HMAC from a secret outside every repository |
| TB2 | Hostile source → tripwire and model discovery | Redacted source bytes matched by the lexical tripwire; whole redacted source files sent to the model, whose reply comes back over TB5 | The tripwire is a fixed embedded table of byte signatures, one linear forward search per row with a cap of hits per file (`truncated`), run on the redacted bytes, with no parser; discovery sends only `redact.File` output through the gateway, whole files, never split; the reply is a closed schema of line spans and enums validated against the file, IDs assigned by creep, joined to the tripwire by union only with worst-case flags, and a canary per batch must be found (R19). v0.1's tree-sitter parser in wazero ([ADR 0008](adr/0008-wazero-tree-sitter.md)) is removed |
| TB3 | Code-reading step → deciding step | Reader verdicts and discovery results to the planner | The planner receives only IDs, enums, booleans and bounded numbers; `planner` never imports `reader`, `discover` or `redact` (layer table, `make budget`); types checked by reflection |
| TB4 | `creep` → network | Redacted payloads to model endpoints | `internal/gateway` is the only package that can import networking; redaction first; per-origin consent; allowlist before DNS; TLS except loopback; DNS pinning; non-public addresses refused; proxy variables ignored; no redirects on send; token and call budget; write-ahead `egress.log` |
| TB5 | Model reply → `creep` | JSON from the endpoint | Size cap, strict decoding into closed structs (unknown, duplicate and case-variant keys refused), bounded retries, never executed, never shown to the planner as text |
| TB6 | `creep` → its outputs | Reports, terminal output, exit code | Repository and log strings escaped in Markdown and on the terminal; SARIF URIs percent-encoded; incomplete runs exit 4, never 0; reports written by remove-then-exclusive-create inside `.creep`; a report that cannot be removed or written is named on stderr and the run never exits 0 (#209) |
| TB7 | Contributors and dependencies → `creep` | Pull requests, Go modules, CI actions, releases | Dependency allowlist with ADRs, import and reach rules, pinned workflows, CODEOWNERS, rulesets, the agent loop |
| TB7a | The Action → the user's runner and pull request (#29, ADR 0023) | A downloaded release, the event, the pull request's checkout, its reports into code scanning and a comment | Checksum and build provenance verified before use; event allowlist and no model key on a fork's pull request; values only through `env`; every exit code but 0 fails the job; baseline from the base commit; the comment carries only creep's escaped Markdown report (§4.7) |
| TB8 | `creep` → other programs | Model CLIs (#6, contract command); gitleaks and osv-scanner (#221, ADR 0013); the docker or podman CLI (#21, ADR 0016) | Only `internal/gateway` (model CLIs), `internal/scanrun` (scanners) and `internal/sandbox` (container runtime) start programs (`make budget`). The runtime CLI: final path outside the repository and working directory, only an `.exe` on Windows, local endpoint only (pinned `--host`), fixed environment and arguments, every container hardened (§4.6). Model CLIs run only through `EgressLog.Exec` after consent, budget and the write-ahead `egress.log` line ([ADR 0014](adr/0014-command-model-through-gateway.md)): argv split without a shell; final path outside the repository and working directory (links, junctions and `\\?\` resolved, compared by file identity), no device or UNC path; minimal environment; empty working directory under the user's private cache directory, never the system temp directory; timeout and stdout cap; process group killed on Unix; tool canary. Scanners: the final path outside the repository and working directory (links and junctions followed, compared by file identity), only an `.exe` on Windows, fixed offline arguments, no shell, creep's own tool config, empty `PATH`, fresh `HOME`/`TMP`/cwd, proxies at a closed loopback port, no keys, timeout and output caps; the project file cannot set `scanners.enabled` (#62). §7 lists what the other parts need |
| TB9 | Model PoC → runner container → app (#24, [ADR 0019](adr/0019-poc-templates.md)) | A template ID and closed parameters from the model (TB5), rendered by creep into raw HTTP requests; the app's responses back | `verify.Request` is a closed struct checked by `Validate` before anything runs: enums and bounded strings over fixed alphabets, no host, scheme, port, framing or forwarding header; creep writes `Host: app:<port>`, the payloads and the probe, and decides every oracle per template (none takes its success value from the model); the requests travel only as read-only files mounted into one runner container whose fixed script reaches only the app (`sandbox.Exchange`, after the canary); the app's responses are read strictly and only judged, a session taken from them is checked to header-safe alphabets. Since #25 the PoC request's user turn is only the reader's redacted slice (TB5), and the runs' requests and responses reach `.creep/bundles` only through `redact.File` (X19-X21, [ADR 0020](adr/0020-poc-repetitions-and-bundle.md)) |
| TB10 | Recipe → reader (#33, [ADR 0025](adr/0025-recipes.md); installed recipes #34, [ADR 0028](adr/0028-recipe-install-and-lock.md)) | A recipe file the operator names, or one `creep recipe add` installed from the operator's clone of a pinned source: signatures, a hint, fixtures and an optional PoC, written by a third party | Strict closed JSON, bounded and refused whole on any fault; the hint and fixtures only through `redact.File`, the reader and the gateway, the hint as escaped `~ ` lines of a labeled HINT block; no planner import on any path from `internal/recipe`; the PoC checked like a model's; a recipe loads only when its fixtures pass; an installed one only when its `creep.lock` checksum matches and the policy's `recipe_sources` allows its source; never from the scanned repository or a config layer (§4.8) |
| TB11 | Calling agent → `creep mcp` (#32, [ADR 0027](adr/0027-mcp-server.md)) | MCP JSON-RPC over stdin and stdout from a coding agent that may be under prompt injection: tool names and arguments in; findings, evidence and scan outcomes out | Only stdio (`IOTransport`), no network transport linked (`internal/tools/linkcheck`); a 1 MiB message cap; every argument schema-checked by the SDK and bounded by `internal/mcp` before anything runs (paths `report.ValidPath`, IDs `report.ValidID`, closed statuses, bounded pages); the scan is a pr scan of the listed files with no sandbox, PoC, optional scanner, consent prompt, calibration run or state-key creation; every path and error returned escaped and bounded |

## 3. Attackers

| Attacker | Controls | Wants |
|---|---|---|
| **Malicious repository** (the default case: `creep` is run on code nobody vetted, including pull requests) | Every byte of the tree: code, comments, file and directory names, links, `creep.yaml`, a pre-made `.creep/` | Run code on the scanning machine; exfiltrate secrets or code to its own endpoint; steer the planner; hide a vulnerability; make an incomplete scan pass a CI gate; inject markup or terminal sequences into reports; exhaust CPU or memory |
| **Malicious or compromised model endpoint** (also: a model fooled by repository text) | Every reply byte, status code and redirect | Get output executed; reach the planner; inject into reports; burn the budget; get code re-sent elsewhere; lie about vulnerabilities |
| **Network attacker** | DNS answers, routing, a proxy, plain HTTP | Read or alter traffic; make `creep` reach internal services (SSRF, cloud metadata) |
| **Malicious recipe or preset** (presets: §4.2a C6; recipes: §4.8) | A data file merged into creep (presets are embedded) or installed by the user (recipes) | Run commands; loosen redaction or gates; point at another endpoint |
| **Prompt-injected calling agent** (`creep mcp`, §4.9) | Every tool call and argument the agent sends over stdio; it reads every reply | Make creep write or change files (apply a fix, rewrite a baseline, write outside `.creep/`), start containers or PoCs, reach the network, read outside the repository, burn the model budget, or carry repository text into its own instructions |
| **Local user** on the same machine (another account) | Shared directories, links, file permissions | Read `egress.log`, payloads or state; plant consent or state |
| **Malicious contributor or upstream** | A pull request, a dependency, a CI action | Ship a backdoor, add a network or exec path, weaken the review loop |

## 4. Threats and mitigations

Tests are in the package named, as `file:Test`; "budget" means `make budget` (`internal/tools/budget`), which CI runs as a required job.

### 4.9 MCP server (#32, [ADR 0027](adr/0027-mcp-server.md))

### 4.10 creep-bench (#35, [ADR 0030](adr/0030-creep-bench.md))

`creep bench` runs an embedded corpus through the scan pipeline and publishes the scores. Its inputs are creep's own data, not the scanned repository; the attackers are a **malicious model endpoint** (live runs), a **malicious contributor** (corpus and fixture changes) and anyone who would trust inflated numbers.

| ID | Threat | Mitigation | Held by |
|---|---|---|---|
| B1 | Published numbers are not what the fixture gives, or a planted fixture changes them | The fixture and corpus are embedded in the binary; `--replay` reads no file, config or state and serves only the embedded fixture, never through the scan's run-state cache, and a request it has no reply for fails the bench (exit 3) instead of scoring a gap; CI replays it and compares the output with `docs/bench/results.json` and `results.md` byte for byte; the fixture is read strictly (version 1, sorted unique SHA-256 keys, no unknown field or trailing data, 8 MiB) | `cli/bench_test.go:TestBenchPublished`, `TestBenchReplayMissFails`; `bench/fixture_test.go:TestParseFixtureRejects` |

## 6. Result honesty

A scanner that silently skips work is a security problem: a CI gate would pass code nobody looked at (A5).

- Every finding is `verified`, `probable`, `discarded` or `not evaluated`; every class is covered, partial or not evaluated (`report/report_test.go`).
- An incomplete run (the scan stopped, a run cap was hit, a file was refused, a sink was left unplanned, the run log did not end complete) is marked incomplete in SARIF, JSON and Markdown and exits 4, which wins over the gate's 1 ([ADR 0007](adr/0007-exit-code-incomplete.md), [ADR 0009](adr/0009-scan-and-why-contract.md); `exitcode/exitcode_test.go:TestForReportNeverCleanWhenIncomplete`, `report/report_test.go:TestIncompleteMarkedInEveryFormat`, `cli/scan_test.go:TestScanExitCodes`).
- The scanned repository's `creep.yaml` cannot shrink what a passing run covers: a lower budget, model timeout or output cap ends the run incomplete, and `scanners.enabled` cannot be set there (R4; `cli/projectstarve_test.go:TestProjectFileCannotStarveScanIntoPass`).
- The data-handling section is read from `egress.log` and fails closed on any line it cannot account for (`report/egress_test.go:TestSummarizeEgressFailsClosed`).
- Since #265 every source file, in any language, is read by discovery; a file not read in full (`too_large`, `redact_failed`, `send_failed`, `budget`) or a batch whose discovery canary the model missed (`parse_failed`) is listed and makes the run exit 4, and no model reply can remove a candidate or lower its risk (R19; `cli/scan_discovery_test.go:TestMissedCanaryIsIncomplete`, `cli/scan_languages_test.go:TestScanEvaluatesAnyLanguage`, `cli/discoverymap_test.go`).
- The gate of the scan's mode decides exit 1: `gates.pr` for a pr scan, `gates.nightly` and `gates.pr` for a nightly one, so a nightly scan never passes what a pr scan fails. A nightly scan whose verification did not run (sandbox off, unavailable, a PoC candidate not run) reads `gates.nightly` at probable, so it never exits 0 on findings at that severity that verification never tried; a finding no PoC template can verify is read at probable in every nightly run (a baseline entry accepts it, ADR 0022); a probable high finding whose PoC ran and never verified still exits 0 (ADR 0021 residual) (`cli/gatemode_test.go:TestNightlyNeverPassesUnverified`, `TestNightlyNeverLooserThanPR`, `TestNightlyIncompleteWinsOverGate`, `TestNightlyBaselineAcceptsUnverifiable`, `config/mode_test.go:TestUnverifiedGateNeverLoosens`).
- An incremental scan (`--changed`, #26) never reads as a full one: every unchanged source file is listed `unchanged` in every format, text, Markdown and SARIF mark the run incremental, and a gap in a listed file still exits 4; its exit 0 says only that the listed files are clean (R22; `cli/changed_scan_test.go:TestScanChangedEvaluatesOnlyListedFiles`).
- A finding is `verified` only when a PoC verified it in at least one of its runs; 0 of 5 leaves it `probable`, so the app the repository builds can never discard or lower a finding (X19, ADR 0020). JSON v1 reads `verified` for 1 to 5 of 5; the rate is in the text, Markdown and SARIF reports.
- A baseline (`--baseline`, #27) never makes a run clean by hiding work: it only keeps a probable or verified finding from the gate until its entry expires, the finding stays listed with its suppression in every format, a not-evaluated finding is never suppressed, and an incomplete run still exits 4 (R24; `cli/baseline_test.go:TestBaselineNeverHidesIncomplete`).
- creep-bench measures this section's promise: honesty is the share of runs that reported a class `covered` and found its planted vulnerability, and a silent miss (covered, not found) is counted apart; a case of a class creep cannot read must show `not evaluated`, never a claim (ADR 0030, `bench/score_test.go:TestScore`).
- A recorded run replays to the same report and exit code with no model call (`cli/scan_replay_test.go:TestScanReplay`).
- A `--stability N` scan only adds: a sample can raise a finding, never drop or lower one, and an `unstable discovery` label (a property of the model) never moves the gate or the exit code and is worded apart from an intermittent PoC (a property of the app, ADR 0020); a recorded stability run replays to the same reports (R25; `cli/stability_test.go:TestStabilityNeverLowersRisk`, `TestStabilityReplayIsDeterministic`).
- State the repository planted never makes a run clean: a refused `.creep` stops the scan with exit 2 before anything is reported, and a replay that meets an entry that is not a valid recording ends incomplete (exit 4; `cli/scan_state_test.go`). **Residual:** a refused `.creep` that is a link to a directory holding a planted `report.*` is not cleaned up (creep never writes through the link); CI must gate on the exit code, not on the presence of a report file. The Action does (G4, G5): it fails on every code but 0 and publishes reports only after exit 0, 1 or 4.

## 8. Out of scope

- Vulnerabilities `creep` fails to detect: they are false negatives, tracked as issues, not security bugs ([SECURITY.md](../SECURITY.md)).
- An attacker who already controls the user's account, the Go toolchain or the operator's configuration (user file, `--config`, `CREEP_POLICY`, flags): operator layers are trusted by design and may loosen gates. `CREEP_POLICY` must still be absolute, so a misconfigured relative path cannot hand the policy to the repository (R17).
- The model provider's own handling of the redacted data it receives: consent per endpoint is where the user decides that.
